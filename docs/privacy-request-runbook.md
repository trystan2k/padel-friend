## 1. Intake and response

1. **Mailbox.** The privacy mailbox is the address published in the policy (`PRIVACY_CONTACT_EMAIL` in `src/features/privacy/privacy-content.ts`). The owner owns it. Use MFA, no forwarding to shared or public spaces, and cover absences so the mailbox is always owned.
2. **Record on receipt.** Received time, requested right(s), and whether the message repeats an earlier request or is a new, related one. Do not confirm or deny that an account, invitation or provisional record exists before verification.
3. **Acknowledge** promptly with a neutral reference. For in-app requests the case reference (`PR-XXXXXXXXXXXX`) is the reference; for email requests use any neutral reference. A random reference is still personal data while correlated with retained mail: do not call it anonymous.
4. **Route by right.** An erasure request from a signed-in account holder normally arrives in-app (§2). Everything below is handled by email, manually:
   - **Access / export**: assemble only the requester's data, redact other persons' data, deliver through a secure channel.
   - **Rectification**: correct the record or point the user to the profile edit.
   - **Restriction, objection**: assess case by case; record the decision and grounds.
   - **Portability**: provide the data the requester provided, in a structured machine-readable format.
   - **Erasure for someone who cannot sign in or a representative**: verify by email (§3) and then run the same operator tooling (§2) against the case the operator opens for them. **An unclaimed invitee with no account**: verify by email, then `erase-unclaimed` (§3).
5. **Timing (GDPR Art. 12, operational description).** Act and respond without undue delay and in any event within one month of receipt. Where complexity or the number of requests requires it, the period may be extended by up to two further months; tell the requester within the first month, with the reasons. **Verification never restarts the clock.** If no action is taken, say why and describe the complaint route (AEPD for Spain, www.aepd.es) and judicial remedy.
6. **Identity (Art. 12(6)).** Ask for additional information only where there are reasonable doubts about identity, and keep it proportionate. Never ask for passwords. Never ask for routine ID copies. If the mailbox is lost, mistyped, recycled, or an agent writes on someone's behalf: do not execute and do not disclose existence; seek proportionate alternative evidence or representation checks and escalate unresolved cases.
7. **Erasure grounds and exceptions (Art. 17).** Assess per case. Record any refusal or partial retention and its ground: for example the retained, anonymized official history of **other** players (owner decision 1), or a legal claim. Assess whether recipients received the data and whether notifying them is possible without disproportionate effort (Art. 19).
8. **Escalate** to the owner and, where appropriate, qualified legal advice: legal uncertainty or holds, suspected security incidents or data breaches, urgent safety-related cases (harassment, stalking context), contested identity, minors or representation questions. Claim no legal certification.

## 2. In-app deletion requests: operator procedure

The operator command is `pnpm privacy:operator <command> [reference] [options]`. It runs on the operator's own machine with the service-role key from the operator's environment. There is no browser operator route and no public destructive endpoint.

**Environment (fails closed when missing)**

- `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` of the target project. Treat the key as a production secret; never put it in a ticket, a chat or a commit.
- `PRIVACY_OPERATOR_ALLOWED_PROJECTS` (comma list of project refs). Default is `local` only.
- Any non-local project also requires `--allow-production` and a non-empty `PRIVACY_OPERATOR_PRODUCTION_EVIDENCE` (the ticket or approval that authorizes it). Production execution needs separate explicit owner authorization; passing the test suite never grants it.
- Use a machine and a mailbox protected by MFA.

**Steps**

1. `pnpm privacy:operator list` shows open cases as codes only (state, last phase, blocker code, next action, whether verified or armed).
2. `start-verification <ref>` creates a single-use code valid for 30 minutes. The code is printed **once**, on your console, together with the **address on file in Auth**. Only a digest and the expiry are stored; the code never reaches the database. Starting again invalidates the previous code and returns the case to `received`.
3. **You send the code yourself** from the operator mailbox to that address (never to an address typed in the request). Template sketch (adapt per language, keep it short, no account details):

   > Subject: Your Padel Friends privacy request {reference}
   >
   > We received a request to delete the Padel Friends account for this address. To confirm it was you, reply with this one-time code: {code}. It expires in 30 minutes. If you did not make this request, ignore this message; nothing is erased on the request alone.

4. When the requester replies with the code: `confirm-proof <ref> --code <code> --confirm`. The proof is rejected when the code is wrong (five attempts at most), expired, already consumed, or issued for another case, and `--confirm` is mandatory. Verification becomes stale if the account email changes before arming (the arm is refused and verification restarts).
5. `dry-run <ref> [--successors <json>]` is read-only. Review the coarse impact counts, ownership counts and the **blockers**. Successors (communities, leagues, matches that need a new owner) must be consenting, eligible, active, non-provisional members or admins; supply them as `{"communities":{"<id>":"<userId>"},"leagues":{…},"matches":{…}}`. With no successor the approved fallback applies: the community is archived without an owner, unsupported future activity is cancelled, and official results stay.
6. **Resolve blockers.** A `platform_admin_grant` blocker means the subject holds a platform reviewer grant: remove it first (operator-level SQL under the usual access controls), then dry-run again. `successor_invalid` means pick another successor. `unclassified_dependency` / `registry_drift` mean the schema changed after the disposition contract: stop and escalate to engineering.
7. `arm <ref> --plan <json|file>` binds a one-use approval to that case, that subject, this project ref and exactly that plan (revision, fingerprint, impact, successors). Any drift is rejected and needs a new dry run. **The approval expires after 15 minutes** and the claim re-checks that the account is still live and that the Auth address is still the one verified: if the cron has not claimed it in time (`ARM_EXPIRED`) or the address changed (`VERIFICATION_STALE`), the case goes to `blocked` with nothing consumed. Re-arm (expiry) or restart verification with `start-verification` (allowed from either unconsumed blocker, so an expired arm followed by an address change is never stranded), then arm again. The freeze re-checks the verified address before the ban and again as the last check of the freeze transaction itself (under a row lock on the Auth user, so a concurrent email change either lands before the check and is refused, or waits until the freeze committed): if it changed since the claim, nothing destructive happens, the arm is un-consumed and the case is `blocked` (`VERIFICATION_STALE`), so restart verification as above. The ban is recorded on the case (`ban_applied_at`) right before the external call, so even an interrupted attempt cannot strand a banned person: a reclaimed run that finds the proof stale while that ban is unconfirmed lifts it first, and until the unban is confirmed the case cannot be withdrawn, refused or restarted. A freeze that aborts after the ban leaves the case `blocked` as `PENDING_UNBAN` until the unban outcome is recorded: that state cannot restart verification, be armed or refused, and becomes the restartable `VERIFICATION_STALE` only once the ban is lifted. If the temporary ban cannot be lifted, the case is `blocked` as `BAN_LIFT_FAILED` (the person is still locked out): `retry <ref>` lifts the ban through the Auth admin API, after which verification can restart. **After the freeze the case is irreversible** (`irreversible: true` in `list`): withdrawal, verification restart and refusal are refused, only a re-arm or `retry` resumes it, and an address change is no longer a blocker (identity was verified before the freeze and the account is banned): it is recorded as `response_address_changed`, so route the final response (§5) to the address verified in step 4, not necessarily the one now on file. A challenge is also tied to the address it was issued to: if the address changes before the proof, the proof is rejected (`VERIFICATION_STALE`) and verification restarts.
8. **Processing.** The freeze starts a durable **producer pause** for the subject: player-add redrive/dispatch (subject as actor, target or invited address), push claims and new notifications refuse it. Before the destructive phase the processor waits a bounded time for database-provable work to settle (no failure is recorded): the `freeze_quiescence_seconds` setting (15 s by default) and older open database transactions, in 5-second cycles counted per case, at most `privacy_quiescence_max_attempts` (12). If an unrelated long transaction outlasts the cap, the case goes to `blocked` with `QUIESCENCE_TIMEOUT` (freeze kept, nothing deleted): find and end the transaction, then `retry` (the wait restarts with fresh attempts). External outbound work (a leased push job, an in-flight invitation dispatch) cannot be proven finished from inside the database: it is observed, never awaited, and the case records `external_followup`; freeze and ban stop any NEW send. The pause row is created when the case opens and switched on by the freeze (producers take a share lock on it, so a producer admitted before the freeze finishes first and one arriving later is refused); it stays after the case closes (un-linked from the subject), and a dead or withdrawn identity is refused by every producer forever. A late-settling invitation finds the scrubbed operation and does nothing; the same address signing up later is a new person with no link to erased data. Producers also re-check the pause immediately before the external call (invitation send, push delivery), so an admission granted before the freeze cannot send after it. **When `external_followup` is set (see `list`), the case stops at the destructive boundary (`EXTERNAL_FOLLOWUP_ACK_REQUIRED`, after the relational and storage phases and before it becomes `supabase_erased`). Verify and mention the outstanding sends, run `sweep-remnants <ref>` (it deletes Auth users created after the freeze for the erased address that were invited, never signed in and have no profile; everyone else is untouched; output is counts and safe codes only) and then `ack-external-followup <ref>`. The sweep fails closed: if it hits its page cap on a full page it reports `SWEEP_INCOMPLETE` and records nothing, so the acknowledgment stays refused; and because offset paging shifts under deletion, any pass that deleted a shell is repeated from the start and only a deletion-free pass ending on a non-full page is recorded. The acknowledgment (refused as `REMNANTS_SWEEP_REQUIRED` until a sweep completed: the address digest that identifies a shell is destroyed when the case closes, so the order is sweep → ack → the case closes → `record-response`, which also requires the recorded sweep for a flagged case): the case resumes and closes. `record-response` accepts the ack too.** Run `sweep-remnants` again if a late invitation is suspected after the acknowledgment but before the case closes. The existing Worker cron (`*/5 * * * *`) runs the processor sweep. It only executes armed or resumable cases. Phases, each committed before the next side effect: **freeze** (ban in Auth, database freeze: stale tokens are rejected at every boundary), **relational erasure** (the unit B seam, atomic), **storage erasure** (the subject's objects in the three private buckets, then re-listed to prove absence), **Auth deletion** (absence proven, an ambiguous answer is a retry). The case then closes. Withdrawal by the user is possible only until the claim; refusal by the operator only while nothing irreversible has started.
9. **Verify the outcome** with `list`: the case is `closed` (outcome erased). A `blocked` case shows a blocker code and a next action: `operator_remove_platform_grant`, `operator_rearm` (dry-run and arm again), `operator_retry` (`retry <ref>` resumes from the last committed phase; completed phases are never repeated) or `operator_review` (stop and escalate). `RETRIES_EXHAUSTED` means a provider outage outlasted six backed-off attempts: check the provider, then `retry`. `QUIESCENCE_TIMEOUT` means an old transaction kept the pause window open (see step 8); `EXTERNAL_FOLLOWUP_ACK_REQUIRED` and `BAN_LIFT_FAILED` are described in steps 8 and 7. `list` also shows `irreversible`, `external_followup` and `response_address_changed` for the final response (§5).
10. **Manual provider steps (§4)** for the same subject, then the **final response (§5)**.
11. `record-response <ref> [--ack-external-followup]` after you sent the final mail (the flag is required when `list` shows `external_followup`). It stamps the response and sets the purge date to 90 days later (owner decision 4).
12. `refuse <ref>` closes a case that has not started, for a justified refusal (record the ground in the mail). `purge` purges expired case records down to non-identifying outcome counts; the Worker sweep also runs it, so this is the manual fallback.
13. **Kill switch.** `switch intake off` pauses new requests; `switch executor off` stops arming and claiming; `PRIVACY_EXECUTOR_DISABLED=1` in the Worker environment stops the sweep independently. Use them for a suspected wrong-target incident, a provider outage, an unexplained blocker pattern, or a schema change under review. An already frozen subject stays frozen; nothing resurrects erased users. Turn them back on with `switch <intake|executor> on` after the cause is fixed.

Case logs hold safe codes, counts and timestamps only. Never copy subject UUIDs, emails, tokens, storage paths or raw provider errors into notes, tickets or chat.

## 3. Verification for people without an in-app request

For an unclaimed invitee, an awaiting-identity person (an add-by-email with no Auth user), a provisional account, or anyone who cannot sign in:

1. **Challenge the address first** (same rule as the in-app verification, before anything is erased). `pnpm privacy:operator generate-code` prints a one-time code locally (nothing is stored or sent). Email it yourself from the operator mailbox to the address the request names, and require it back within a short time. A reply from another address, a wrong code, or no reply means no erasure.
2. **Account holders are not handled here.** If the address has an Auth user, the command refuses (`ACCOUNT_EXISTS`): that person goes through the case flow in §2 (they can request in-app, or you open the case for them).
3. **Erase the add-by-email record** (awaiting identity: a name and address typed by someone who invited them, no Auth user):
   - `pnpm privacy:operator erase-unclaimed <email>` is a dry run. It prints counts only (operations, recipient sends, throttle hits) and changes nothing.
   - `pnpm privacy:operator erase-unclaimed <email> --confirm` applies it. The address is matched exactly, lower-cased, in state `awaiting_identity` only. The command never echoes the address.
   - If more than one operation matches (several people invited the same address, or retries), it fails closed with `AMBIGUOUS` and the count. Review with the requester, then repeat with `--all-matches` to accept every match.
   - Applying it scrubs the address and name in those operations, removes the capability and its digest, the recipient-send and throttle rows for that address, and clears the dispatch attempt, so no queued or in-flight invitation can create the account afterwards. Only non-identifying facts remain (event, inviter, timing). A second call finds nothing and succeeds. There is no suppression list: a new invitation of the same address later is a new operation.
   - `EMAIL_INVALID` means the address was malformed; an unknown address returns the same zero counts as a blind lookup.
4. Scope duplicates and aliases deliberately (other spellings of the address) and repeat per address. Never match by public search.
5. Include this in the final response (§5): what was removed, and that the inviting player's own records (for example the event they invited to) are unchanged.
6. Authorization never comes from request text, an old session, `email_confirmed_at` alone, knowledge of an invitation, or editable JWT metadata.

## 5. Final response

Send it from the operator mailbox to the verified address, not through the app. State: what was removed, what remains and why (anonymized official history of other players, any exception with its ground), which provider or backup restrictions are outstanding, and how to complain (AEPD) or seek a remedy. Confirm only phases the case actually completed; track incomplete external work instead of calling it complete. Do not call retained records anonymous unless the pseudonymization assessment in the design doc (§8) holds in that community's context; where it fails, restrict or suppress the affected details or block the case pending an owner decision.

## 6. Backups, snapshots and restore

**Current fact (MS, dated 2026-11-27).** [production-backup-plan.md](production-backup-plan.md) and `INITIAL_SETUP.md` state that alpha has **no automated production backups** (Supabase Free plan, status "not implemented", PAF-177). The owner accepts possible data loss during alpha. Whether manual exports, snapshots or provider-managed recovery points exist is **not evidenced either way (PO)**. Make no retention promise about backups to requesters, and say only what is proved and dated.

**Before answering any request, check** whether a recovery point exists: ask the owner for any manual dump or export, check the Supabase dashboard for backups and point-in-time recovery, and check Storage versioning. Record the date and result.

**If a recovery point or export exists:**

1. Isolate it and restrict access. Do not attempt in-place selective deletion.
2. Put it on a verified expiry schedule and record the last-expiry date.
3. Restore only into a **disposable, isolated** environment with mail, Push and public traffic disabled.
4. Before reconnecting anything, **reconcile every erasure performed after the snapshot** (database, Auth, Storage objects, queued invitations). Fail closed: if coverage or the post-cutoff list of erasures cannot be established, do not reconnect.

**Recovery suppression manifest (design, gated).** If an approved automated backup exists (PAF-177 goes live), keep a short-lived, separately encrypted, strictly scoped manifest keyed by the **original** subject identifier (never mapped to the tombstone), valid only until the last applicable recovery point expires. It is personal data: replay it in a protected restore, then purge the identifiers. Do not install a standing identity ledger when no approved backup needs it. Add the restore gate (manifest replay, jobs disabled and publication blocked until replay completes) to PAF-177's definition of done.

**Restore gate (implemented).** A restored environment is an old copy: accounts erased after the snapshot exist again in it. **The authoritative isolation boundary is a marker row**: the restore flow (`restoreSnapshotWithGate`, `runRestoreRehearsal`) runs as the container superuser when it creates the scratch database, sets `app.restore_target = 'on'` and inserts the row of `privacy_internal.restore_isolation_marker` (named after its database, so a dump restored under another name does not count). No client role, `service_role` included, can write that table or make the setting authoritative (a session `SET` alone does nothing), and every restore RPC, `clear` included, refuses with `RESTORE_NOT_ISOLATED` unless both the marker and the setting are present, so a live database cannot be begun, reconciled or have storage planned, whatever refs a caller passes. `restore-gate begin --snapshot-at <iso>` runs against that ISOLATED restore target only (the CLI also refuses any production project outright, before `--allow-production` is considered) and needs the source project in `PRIVACY_SOURCE_SUPABASE_URL` / `PRIVACY_SOURCE_SERVICE_ROLE_KEY` (read-only). It derives the **expected subjects** (live in the restored copy, gone from the source project: closed case records keep no subject id by design, so the difference is the only complete source), proves the set by **count parity** with the source's identity-free erasure events recorded after the snapshot (`privacy_internal.erasure_events`: one bare row of time and a tombstone flag per completed erasure, no subject id, digest or mapping, so it is not an identity ledger; erasures without retained history are counted too). A mismatch is refused as `COUNT_MISMATCH`: an interrupted or unknown condition, escalate (a person who signed up after the snapshot and was erased also counts, so that case stops here for review). Parity applies fully from migration `20261125090000` forward; erasures before it that had no retained history are not reconstructable, so verify those by hand, turns intake and executor off (even when refused), binds the gate to this project and database, and marks the persisted gate (`privacy_internal.restore_gate`) `pending`. A zero-parity empty set is reconciled at once; a later `begin` with the same snapshot extends the open gate (late erasures) and keeps what was reconciled; `switch <intake|executor> on` is then refused (`RESTORE_GATE_PENDING`) and nothing can be armed or claimed. Run it on every restored environment before anything else, and **keep the restored environment disconnected from traffic until the gate is closed** (the gate fences the privacy executor and intake only; it does not publish or block anything else, so isolation is your control). Run `restore-reconcile <subject-id>` for EVERY expected subject in the restored copy: the database refuses anything outside the expected set, a subject with no trace in the copy, another project, or a gate that is not pending. The driver lists the subject's avatar prefix through the environment's Storage API (a listing that fills every page up to its 10,000-entry bound is not complete: the reconciliation is refused as `LIST_OVERFLOW` before any plan exists, and again if the post-deletion listing overflows), the database builds the deletion plan (restored pointers plus that listing, so detached orphans are included), the driver deletes exactly the plan in bounded batches and lists again, and the database accepts the confirmation only when the deleted set equals the plan and nothing is left (`STORAGE_INCOMPLETE` / `STORAGE_LIE`; there is no caller attestation). Then it replays the real erasure and removes the restored Auth record, proves zero residue (every public table, Auth, Storage objects) and refuses on any residue (nothing is changed for that subject). The gate becomes `reconciled` only when the reconciled subjects equal the expected set exactly; `restore-gate clear --evidence <reference>` is refused until then, re-checks count parity against the source (an erasure made while reconciling forces a re-`begin`) and needs an evidence reference (ticket or audit note listing what was reconciled). The reference is persisted as the audit trail, the subject ids are not, and the switches stay off until you turn them on explicitly. Expected-set coverage plus the gate and the switches are the enforceable isolation; keeping the environment away from traffic until the gate is closed remains your operational control. Restored case rows for a subject stay inert while the executor is off. There is no identity ledger behind it.

**Trust boundary and residuals (codified).** The database cannot observe Storage bytes or in-flight HTTP calls. What is enforced is: the plan is computed by the database (restored pointers, including subject-owned attachment pointers that are still non-null in the restored copy, plus the avatar-prefix listing), the trusted operator driver (MFA machine, allowlisted, local target only) executes exactly that plan through the Storage API and lists again, and the database records only equality receipts (deleted set == plan, re-list empty); the rehearsal is the proof artifact that the chain works end to end. Objects whose pointer a pre-snapshot erasure already nulled are NOT recoverable from the restored database: when detaching happened before the snapshot, also list the buckets by date prefix for the reconciliation window by hand and record that check in the evidence reference. Coverage of the expected set rests on count parity with the source tombstones, per-member trace completion (a member with no trace keeps the gate pending, so clearing is impossible) and the `coverage_complete` field re-derived at `clear`; no standing erasure manifest exists because the plan forbids installing one without an approved backup need (PAF-177), so a deliberately offset source discrepancy is caught only by the fail-closed `COUNT_MISMATCH` and escalated, which is this plan's "fail closed when coverage cannot be established" within that constraint.

**Rehearsal (implemented, synthetic data).** `test/privacy-restore-rehearsal.integration.test.ts` seeds a synthetic subject with a fake avatar reference, takes a snapshot of the test stack (`takeSnapshot` in `scripts/release-backup-restore.mjs`), runs the real erasure path, restores the snapshot into an isolated scratch database (`restoreSnapshotWithGate`), and proves: the erased subject exists again only in the scratch copy (the snapshot semantics that make reconciliation mandatory), the restored environment starts with intake and executor off and the gate pending, the switches cannot be turned on and nothing can be claimed, two subjects are erased after the snapshot and the expected set is derived; subjects outside it (random, live, no trace), another project ref, an unconfirmed empty set and a clear before or with partial coverage are all refused with nothing changed; a reconcile refuses on residue and leaves the subject untouched; the fake avatar object is uploaded through the real Storage API before the snapshot, re-uploaded after the live erasure (as a storage restore would), and is gone after its reconcile together with the restored database rows; only the complete set closes the gate, with a persisted evidence reference; and the live stack never regained the account. The scripted restore rehearsal (`runRestoreRehearsal`) applies the same gate to every destination and fails if it is not closed. Both include the `privacy_internal` schema (cases, switches, the disposition contract) and never touch hosted production or Storage objects. Evidence date: 2026-11-27 (local test stack, synthetic data). When PAF-177 turns automated backups on, its definition of done must include this gate and the manifest replay described above.
