## Chosen Approach

- Proposed solution:
  - Change **all** `startLocalSql` callers to `startLocalProcess(process.execPath, [supabaseCliPath, 'db', 'query', '--local', '--output-format', 'json', sql])`. Resolve `supabaseCliPath` inside `startLocalSql` with `createRequire(import.meta.url).resolve('supabase/dist/supabase.js')`, importing `createRequire` from `node:module`. Use package resolution, not cwd-relative path concatenation or pnpm-store paths. Keep resolution lazy so environment-skipped SQL tests do not resolve the CLI unnecessarily.
  - The spawned child is Supabase's own JS CLI entry point, not pnpm or a shell. It remains a launcher for the native CLI, but preserves native signal termination rather than translating it into pnpm's numeric status. This satisfies the request's permitted direct JS-entry-point variant; do not describe it as spawning the raw native executable.
  - Add required `sweepCommand: LocalSqlCommand` to `HolderTeardownResult`, return the retained handle alongside existing `elapsedMs` and optional `sweep`. Other callers ignore the additive field; no ownership or cleanup responsibility transfers to callers.
  - Stalled-sweep test checks defined sweep result, defined command PID, `sweep.code !== 0`, `!sweepCommand.isGroupAlive()`, and existing elapsed bound. Avoid optional chaining for the exit assertion: explicitly guard missing `sweep` after `toBeDefined()` so `undefined !== 0` cannot pass.
  - Choose **not-clean-exit**, not mandatory `toBeNull()`: current signal kills produce null, but a CLI handling termination through its own nonzero exit remains valid. No pnpm-version status allowlist. PID assertion prevents an immediate spawn failure from masquerading as successfully reaped child; full-file happy-path SQL assertions catch broken entry points/native binary availability.
  - Comment at spawn explains pnpm-wrapper versus CLI signal distinction; short test comment explains nonzero exit plus group probe is intentional contract, not exact wrapper encoding. Update stale `pnpm → supabase CLI → psql` process-tree comment in `startLocalProcess` to generic child/descendant wording.
- Justification for simplicity:
  1. **Selected: shared direct CLI JS-entry spawn.** One helper change, one additive result field, focused assertions. All SQL children gain wrapper-free process-group ownership; `runLocalSqlBounded` still stops commands on deadlines. `process.execPath` bypasses POSIX `.bin`/Windows `.cmd` differences and handles paths containing spaces without shell quoting.
  2. **Rejected: sweep-only direct spawning.** Smaller caller blast radius, but duplicates SQL launch policy and leaves holder/polling commands coupled to pnpm. Shared helper already centralizes arguments and bounded cleanup.
  3. **Rejected: native-platform package resolver.** Removes Supabase's own signal-preserving launcher too, but duplicates its architecture/Linux-musl/override selection and depends on optional-package internals. No benefit required by acceptance criteria. Direct `.bin` invocation is permitted but less portable than the verified JS entry point.
- Components to be modified/created: `test/community.admin.integration.test.ts` only: import, `startLocalProcess` comment, `startLocalSql`, `HolderTeardownResult`, `releaseHolderAndSweep` return, stalled-sweep test/comments. Windows launch becomes portable; **POSIX process-group behavior remains existing suite scope**, including unconditional sibling `sh -c` test and negative-PID probes. Do not claim Windows process-group coverage or add unrelated Windows cleanup support/skips.
