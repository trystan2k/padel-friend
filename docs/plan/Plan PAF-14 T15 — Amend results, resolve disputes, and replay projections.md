## Chosen Approach

- Proposed solution: Extend existing result version/review pipeline with amendment/dispute decisions and **one active official confirmation pointer per game group**. Keep every historical confirmation. Append source/invalidation revisions to existing stable rating identities; reuse PostgreSQL full merged-stream replay and statistics/League rebuild helpers. Persist small repair jobs/attempts; process one correction atomically per attempt through existing pg_cron pattern. No browser service-role access, TypeScript rating arithmetic or partially visible staging generations.
- Justification for simplicity:
  1. **Chosen — atomic full replay + durable retry metadata.** Existing rating engine already reconstructs global history. Full replay safely includes transitive downstream opponents/partners across communities; expected product scale explicitly favors correctness. Failed attempt rolls back sporting changes, retains durable diagnostics and retries from committed state.
  2. **Rejected — per-player incremental dependency closure with chunked staging/revision publication.** Smaller runtime scope but needs graph expansion, multi-generation state, cursor persistence and fencing at every chunk. Unnecessary until measured full replay cannot meet production transaction limits; not an automatic follow-up or permission to omit scale validation.
  3. **Rejected — reverse deltas/update ratings directly.** Ratings are nonlinear and checkpoint/config-dependent; cannot correctly repair downstream history. Also destroys provenance or duplicates logical events.
- Components to be modified/created: New additive migrations after 20261104090000; small result-amendment contracts/commands in src/features/matches; bounded repair contracts/server functions + diagnostics presentation in a small src/features/result-repairs slice; existing player rating readers, League readers/history, statistics SQL readers, notification/audit producer/target support, thin protected route adapters, three locale catalogs, test/helpers and e2e fixtures. ### Precise replay and publication algorithm (T15.3 owns; T15.4 completes dependent publication)

1. **Acceptance vs publication:** player approvals, no-rejection auto-confirm or explicit Admin override persist accepted candidate + queued correction command. Prior official pointer remains active until successful repair. Candidate DTO exposes pending/failed application separately from proposal approval. A first confirmation with no prior official fact uses existing synchronous finalizer instead, never correction invalidation. Units 1–2 install contracts but must not expose a shortcut that switches facts before complete projector exists.
2. **Claim/retry:** singleton trusted processor claims queued/due failed or expired-lease job, assigns fresh UUID fence token, increments attempt and commits claim before execution. Existing cron pattern may use separate named claim and processing calls/ticks; user server action may call claim RPC then execute RPC in separate transactions for immediate progress. Job remains recoverable if caller dies between them. Processing/reclaim both lock same job row and validate token; stale worker never publishes. Reclaim cannot steal job from transaction actively holding row lock even when lease wall clock expires. Use bounded backoff; exhausted automatic attempts remain failed/operator-visible, not succeeded. Explicit authorized retry resumes same logical job.
3. **Locks:** use documented graph community UUID order → event/registration/source/profile FK coverage → League UUID order → global rating projection → statistics. Full replay's safest bounded implementation prelocks current communities in UUID order, then needed source/FK rows and affected Leagues before global lock. Include correction's old/new players and source rows; reuse/extend rating_projection_lock_covered for effective-source coverage, including already-ledgered replacement sources. Re-read coverage after acquiring rating lock. Gap releases inner subtransaction locks and retries boundedly; never add upward locks. New communities/confirmations racing preflight require coverage recheck. No path from global rating lock back to community/League/event. Claim/retry job-row locking must not form reverse edge with enqueue: enqueue never waits for global claim/job while holding sporting locks. Prove through separate-connection tests.
4. **Base check:** under locks, validate job token/status, active base confirmation and candidate approval still valid; actor decision already immutable. Stale base/canceled/superseded candidate becomes explicit conflict, no blind rebase. Read latest committed_revision R, allocate R+1 only inside publication transaction. Two corrections same group cannot both replace same base. Unrelated new confirmation/admin adjustment committed before lock is included in fresh replay; never use stale queued rating state.
5. **Fact selection/invalidation:** insert immutable corrected confirmation (or void decision), switch official pointer inside repair subtransaction. Append inactive source revisions for old quartet; append active source revisions for corrected quartet only when corrected fact ratable. Unchanged quartet reuses logical identities. Friendly/Incomplete/void create no active competitive effects. Invalidated facts do not get compensating competitive games. Effective sources of all unchanged later groups remain active.
6. **Scope/order:** replay FULL global merged stream from immutable initialization evidence, not one community or just original quartet. Earliest potential invalidation key is min(old played key,new played key); full replay reconstructs prefix and all downstream dependencies automatically. Match order exactly (effective played_at, stable game_group_id, kind 0, revision tie slot 0). T14 checkpoint order (stored boundary_played_at, stored boundary_group_id, kind 1, original projection_revision). Changing confirmed_at never changes tie order. Reordered corrected played_at uses same stable group ID. Multi-group same-event and unrelated later events remain included once.
7. **T14 preservation:** never update adjustment decided_at/effective_at/boundary/revision/reason/target. At original stored boundary apply absolute approved target mu/display level; sigma and actual competitive count flow through reconstructed prefix, peak uses existing checkpoint semantics; reliability preserve flows through, reset/reduce applies recorded target and exception flag. Append changed reconstructed checkpoint state at R+1; original administrative before/after audit remains unchanged. Same-key match precedes checkpoints; equal-key checkpoints ordered by original committed revision. No backdating to corrected match date; no rerun of old admin permission/review/approval workflow. Include users with now-zero active games so voiding their last match resets materialization to initialization plus surviving adjustments.
8. **Versions:** unchanged groups replay their recorded engine/config, not current default. Replacement inherits corrected game's recorded calibration provenance; new quartet members use same group stamp. A previously nonratable group becoming ratable takes explicitly frozen engine/config at accepted correction, persisted before processing, never job execution default. Existing 1.1.0 exception dispatch remains deterministic when replayed prefix carries exception; do not blindly retain 1.1.0 if correction moves group before original exception. Unsupported/missing recorded config fails closed and logs diagnostic. Test config selection independently of available single production config; use existing unsupported-version oracle and transaction-local test configuration if engine supports another valid config, never modify frozen production kernel to fake coverage.
9. **Append/exactly once:** calculations written only if inputs/output/effective source/kernel stamp changed; unique event/revision plus source identity constraints prevent duplicates. Inactive effects excluded from current counts/history/last-game checks and statistical rating rows. Preserve audit at prior revision. Recompute removed users, new users, transitive users, watermarks, highest level, reliability and rank inputs from active stream. Same correction retry after successful commit returns original receipt/revision; no second calculations, snapshot or notification. A later intentional correction is separate job/new revision, not retry.
10. **Dependent publish:** while holding proper pre-acquired locks, T15.4 rebuilds League counters/snapshot, replaces corrected group statistics, refreshes all replay-changed rating facts/summaries/ranks using old+new dimension worklists. Update projection control committed_revision exactly once, validate consistency, append completion audit/notification, mark job succeeded, commit all together. Other readers see old coherent snapshot or new coherent snapshot through MVCC, never partial repair. Do not separately publish corrected match before statistics/League success.
11. **Reads:** preserve rating_read_assert_revision against committed control. Current history/explanations/rating statistics resolve source and calculations at same committed revision; old client cursor receives RATING_REVISION_STALE after publication and reloads, including adjustment union branch. Expose pending/failed repair metadata separately from official result. No partial “latest” calculations above R, no caches of private SSR data. Historical audit RPC explicitly requests old revision with independent authorization; do not weaken current-reader guard to expose it.
12. **Failure/resume:** executing RPC wraps all sporting changes in exception subtransaction; failure at any replay/publication stage rolls back pointer/source/calculations/ratings/League/statistics/control/notifications. Outer transaction records failed attempt/code/retry time and returns structured failed receipt (not exception that would roll back diagnostic). Process termination/connection loss rolls back execution transaction; previously committed claim expires and is reclaimable. Retry recomputes from current committed state, not half-written cursor. Inject mid-stream and after-League/before-statistics failures; prove complete rollback and eventual equality with clean run. Progress stage need not be falsely live: show durable attempt start, running/stale lease and last failed stage/time; mark success only after committed receipt.
