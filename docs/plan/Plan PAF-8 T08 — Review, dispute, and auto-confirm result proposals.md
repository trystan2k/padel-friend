## Chosen Approach

- Proposed solution: SQL-owned result state machine using existing proposal identity + immutable fact versions, append-only review evidence, one immutable confirmation record/event, existing command/audit infrastructure and existing pg_cron pattern. Browser capabilities are advisory; SQL repeats every eligibility/version/deadline check under lock. Parent resolution derives from frozen expected groups plus confirmed identities, never from count of submitted proposals.
- Justification for simplicity:
  1. **Selected — transactional SQL + existing cron/notification store:** reuses delivered lock/security/replay patterns; facts, confirmation, audit and notifications share transaction. No application-side compare/write race, new queue or second official-facts copy.
  2. **Rejected — Workers scheduler + application-layer fanout:** adds secrets, HTTP retry surfaces and split transactions. Consider only if actual pg_cron prerequisite fails and caller approves equivalent trusted runner invoking same SQL processor.
  3. **Rejected — generic event sourcing/workflow engine and early projection implementations:** unnecessary framework; immutable version rows + narrow confirmation event are sufficient. Do not build T10/T12/T13 now.
- Components to be modified/created: new SQL migrations for review domain, transitions, scheduler, read projections and notifications; src/lib/supabase/database.types.ts per schema unit; result model/validators/functions/error-copy/form/UI/controller; result_resolution decoder/card/banner/detail integration; existing notifications feed/detail/targets with typed result context; existing catalogs and fixture/test infrastructure. ### Transactional contract and state machine

**Identity and data model**

- Keep proposal UUID stable for (match_event_id,group_number). active_version selects full immutable facts. Add version-local submitted_by/submitted_at/review_deadline_at metadata, backfilled for delivered v1 rows from pointer. New corrections write metadata with fresh DB clock; pointer's current submitter/time/deadline move together. Preserve old metadata forever.
- Widen pointer status CHECK to pending/disputed/confirmed. Replace unconditional pointer UPDATE guard with narrow transition guard: identity/event/group never change; DELETE denied; pointer version advances exactly +1 only while unconfirmed; same-version status may only pending→disputed/confirmed; corrections pending/disputed→pending + version+1 reset provenance/deadline. Confirmed pointer cannot change. Maintain active-version FK/integrity using deferred constraint checks where insert ordering requires it; deadline always equals current version submitted_at + 48 hours.
- Keep version rows append-only. Backfill new metadata before reinstating guards within migration transaction; preserve scoring/time/team CHECKs. No session-GUC flag that browser callers could forge to bypass guards. RPC grants are primary write boundary; guards constrain valid internal writes as defense in depth.
- Add match_event_result_reviews: immutable id, proposal_id/version FK, reviewer_user_id, decision approve/reject, reason_code/note for rejection, decided_at, request_id. Unique(proposal_id,version,reviewer_user_id,decision) prevents duplicate effective votes; actor cannot count twice. Approval→rejection remains possible while partial review is pending, by appending rejection; no rejection withdrawal/reopening same version. Same approve with new request ID becomes no-op, not new audit/alert. Submitted teams, never current UI/FIFO position, determine team eligibility.
- Add match_event_result_confirmations: immutable id UUID (the **confirmation_id** and **ResultConfirmed event identity**), proposal_id UNIQUE, proposal_version FK, event/group unique, source MANUAL/AUTO_48H, confirmed_at, effective_at (deadline for AUTO_48H, decision time for MANUAL), actor_id nullable only AUTO_48H. Store frozen event_type/ratable eligibility needed by future consumers or derive from protected immutable event facts. Refer to immutable version for authoritative teams/sets/played_at; do not copy facts into another result table. This row is official-result fact pointer AND durable domain event; no redundant outbox/event table.
- RLS on all new public tables; revoke all direct writes and internal helper EXECUTE from PUBLIC/anon/authenticated. Expose only authenticated, non-anonymous authorized RPCs. Official-results reads and review evidence use event creator/current community admin/accepted event participant checks consistent with existing private proposal reader; no new public identity leak.
- Extend management command actions for review_result/correct_result; reuse (event,actor,request_id) + normalized full payload equality. Extend match_event_audit_log actions for result_approved/result_disputed/result_corrected/result_confirmed. Add nullable confirmation_id FK with uniqueness for confirmation audit; action/source restrictions permit null actor for automatic confirmation only. Audit stores proposal/version/source/team/reason and changed fields; registration transition_revision is an existing provenance snapshot, NOT confirmation identity or a new FIFO revision.

**Transitions**

| From | Command | Preconditions | Atomic effects |
| --- | --- | --- | --- |
| Awaiting result | existing submit | existing creator/admin + frozen-quartet/scoring checks | v1 Pending, submitted_at DB time, deadline +48h; review-required/info alerts |
| Pending(v) | approve | expected v matches; eligible approval; before deadline | Append one vote/audit. If required team coverage reached, same-transaction confirmation; otherwise stay Pending |
| Pending(v) | reject | expected v; eligible rejector; valid reason; before deadline | Append rejection/audit; immediate Disputed; no official facts; scheduler no longer eligible |
| Pending/Disputed(v) | correct | expected v, creator/admin, still unconfirmed; pending version not already due | Append immutable v+1 with revalidated facts + new submitter/time/deadline; move pointer to Pending; old reviews retained but ignored |
| Pending(v) | due processor or eligible late command | DB time ≥ deadline; same current version; no rejection evidence | Shared finalizer creates exactly one confirmation, changes status, audit, lifecycle notifications |
| Confirmed(v) | retry | matching identity/request replay | Return same confirmation_id; no writes; new incompatible review/correction returns typed terminal conflict |
| Disputed/superseded | stale approve/reject/job | no valid current pending target | Typed conflict/no-op, never confirmation |

**Eligibility**

- Compute submitter side from *active version's* submitted_by and immutable teams. Playing submitter: only opposite side can approve; own teammate/submitter cannot count. Nonplaying submitter (including admin): one distinct approval from each side needed. Admin status alone grants no review vote.
- Proposed rejection pool per clarification above. All actual players see facts, submitter/deadline/version/approval progress/dispute reason; other authorized event readers see appropriate read-only group states. Show each action only when its SQL capability is true; already-approved eligible reviewers may still reject a partially approved version. No reviewer/no approvals/partial approvals do not prevent timeout.

**Lock, replay and clock order**

1. Verify authenticated non-anonymous actor (scheduler is internal and has no browser grant). Resolve proposal→event identity without taking proposal lock.
2. Acquire existing canonical chain via lock_match_event_registration(event_id), then proposal FOR UPDATE. All writers use this ordering, including corrections and scheduled confirmation. Scheduler uses corresponding skip-locked helper *before* proposal lock; never claim a proposal first then acquire event/community locks.
3. Authorize actor, check normalized command replay first for same actor/request, then expected version/current terminal state. A replay returns original receipt even after later lifecycle changes, but never leaks across actors. Payload mismatch returns idempotency conflict.
4. Take clock_timestamp AFTER lock acquisition; never rely on transaction-start now() or browser time. For valid current pending target, if at/after deadline, finalize AUTO_48H before accepting a late manual decision/correction. Return terminal/current-state response without throwing afterward (an exception would roll back auto-confirmation). Unauthorized or stale-version calls cannot trigger finalization of newer facts.
5. Before deadline apply decision/correction; count distinct eligible actors by required sides and active version, not raw approval count. Shared internal finalize_match_event_result_locked(proposal_id,expected_version,source,actor) independently rechecks pending/current/no rejection and either manual coverage or actual DB due time. It cannot take a caller-selected time or allow an untrusted MANUAL/AUTO bypass.
6. Insert confirmation + status transition + audit in same transaction. Unique proposal/event-group keys make a second finalization return existing identity, never recreate official rows. Unit 6 attaches synchronous notification triggers to first-created evidence/confirmation rows; failed fanout rolls back whole transition and retries safely. No app-layer post-commit notifications.
7. Any rejection committed before competing finalization obtains lock wins and blocks it. If sufficient approval commits first, group is terminal and later rejection is a conflict. A request merely initiated before deadline is not a committed rejection; linearization point is lock-protected DB check. Race tests prove both orderings; no unsupported promise that wall-clock button-click order wins.

**Corrections and official history**

- Reuse fact-validation seam from submit_match_event_result (extract bounded private helper if necessary); do not call current submission RPC for correction, since it deliberately rejects existing proposals. Preserve identical frozen quartet, unique team members, score/time/court rules; validate proposed team repartition anew. Current submitter may differ from v1, so reviewer policy recomputes.
- Old votes/rejections never carry forward; rejected version remains audit-visible as superseded, not overwritten. Correcting does not thaw results_protected_at or modify registrations/event type. Stale version requests fail, including old notifications.
- Expose official-result reader joining confirmations→exact version, not active pending pointers. Friendly/Incomplete confirmed records are factual history but no rating/reliability/League effect; competitive eligible confirmed records expose ratable flag for later consumers. Future T10/T12/T13 must key application/receipts uniquely by confirmation_id, not submit RPC request_id, played_at or notification ID. Contract test proves manual/auto/retry expose same identity.
- Parent result_resolution: awaiting_results when no confirmation exists; partially_resolved when ≥1 but fewer than frozen expected group_count confirmed; completed only when every expected played group confirmed. Missing/unsubmitted groups count unresolved; Pending/Disputed groups stay visible. Cancelled/incomplete/no-playable-group conditions remain distinct; zero groups never vacuously completed. Derive summary in SQL from frozen roster and confirmations; add to event detail/list projection, keep existing operational open/cancelled intact. Atomic confirmation commit changes derived parent state without redundant writable status store.

**Trusted scheduler**

- Internal process_due_match_event_results(limit default 25, bounded 1..100), partial pending/deadline index; named minute job padel-friend-match-result-auto-confirm. Finite cadence means confirmation executes at first successful tick at/after 48h, never before; effective_at preserves exact deadline. Browser never finalizes based on countdown reaching zero.
- Select due candidates without row locks, process via canonical skip-locked chain + proposal lock, re-read active version/status/deadline, call common finalizer. Concurrent cron runs/manual calls are harmless. Per-proposal attempt/failure metadata in separate internal processing-state table avoids confusing lifecycle pointer immutability; fairness oldest/least-attempted ordering, failed-item subtransaction rollback, durable sanitized error details and bounded backoff. Failure/lock skips must not starve later due proposals. Do not write failure metadata while holding proposal-first locks or block on failed NOWAIT path; use bounded nonblocking bookkeeping and test contention.
- Corrections reuse proposal ID, so pending candidate eligibility always re-reads active version/deadline; failure/backoff metadata resets/version-scopes at correction. Old job selection can never confirm corrected facts early. Downtime catch-up selects all still-due pending versions; disputed/confirmed excluded.
- Unit 6 adds reminder/readiness producer to same trusted processing entry point, separately bounded so it cannot delay due confirmations. Verify named job singleton, grant restrictions and real execution; deployment checks fail explicitly if provisioning only emitted notice. Mitigation: unschedule named job/revoke new mutation RPC grants to stop writes; preserve confirmations, versions and audit. Forward-fix only after official facts exist; never delete/replay confirmed identities as rollback.
