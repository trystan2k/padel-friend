## Chosen Approach

- Proposed solution: Reconcile routes, rendered states and reference ownership first. Stabilize typography, tokens, primitives and shell before page baselines. At each unit, implement the approved composition at existing feature seams, retain contracts, and land structural probes, screenshots and regression evidence together. U24 certifies and finishes reference-source migration; it does not create missing first-pass coverage for earlier units.
- Justification for simplicity: A wholesale rebuild would change unrelated contracts, destroy intermediate reviewability and make regressions hard to isolate. Page-first forks or an indefinitely parallel legacy/Clubhouse shell would duplicate controls/tokens and generate screenshot churn as fonts, geometry and navigation change. Foundation-first slices preserve one application and one navigation owner; reuse existing components, route adapters, data and fixtures. Approved temporary compatibility is acceptable only where needed to preserve reachability or keep untouched tests valid between commits, with a named removal owner in this epic.
- Components to be modified/created: Token JSON, Style Dictionary output through build, Figtree dependency/root imports; shared UI and presentation states; shell/navigation and thin existing route adapters; feature directories for U5–U23; localized keys in en/pt-BR/es; colocated StyleX; approved reference exports/manifests, existing Vitest and Playwright contracts and fixture builders. New composition/routing, asset treatment or domain fields beyond known scope require explicit decisions where noted. No second design system, theme context, synthetic production data or broad rewrite.

## Implementation Steps

### Operating contract for all units

- **Entry:** Confirm predecessor evidence, unit inputs and Linear approvals. Read relevant redesign details and inspect approved frame IDs, nested states, dimensions, variant names and annotations. Dry-run the route/state and interaction checklist before edits; inspect current call sites, loader/search contracts and UI tests. For new fields/actions establish existing data source, null/unavailable behavior, and permission owner before rendering. Do not restyle a missing-design surface. Distinguish inherited foundation changes from page-level restyling; if a shared change would visibly redesign a blocked page, record/approve the impact or isolate it with an existing compatible variant.
- **Build:** Serena edits per repository protocol. Keep route modules thin; put UI with feature owner. Semantic token → matching primitive → justified new token only; StyleX, `src/styles.css` reset only. Use Base UI for interactive widgets; native semantic links/forms/tables where appropriate. Preserve accessible names, focus, keyboard, error/status announcements and reduced-motion behavior where applicable; ≥44px hit areas, fluid layout and safe-area insets protect sticky actions. All copy, labels and status text in en/pt-BR/es; reuse request-local i18n and SSR-consistent theme/locale. Do not derive behavior from a frame mock. Record each approved frame/state and any adaptation in the owning issue.
- **Ship:** Put page-specific fixture cases, structural and visual tests next to implementation in same unit. Before commit: fast gate (`pnpm typecheck`, `pnpm lint`, affected `test/**/*.test.ts` via existing unit/related config; record actual test count, not a zero-test success). QA verifies affected DB/E2E on that intermediate state where needed. Keep one commit per unit with scoped files, Conventional Commit and no Linear IDs; record SHA, files, fixtures, frames, exact commands, observed results and review links. No per-unit push. Keep the app navigable and regression suites coherent at each boundary. If shared metrics legitimately invalidate an untouched screen's transitional Chromium baseline, validate its existing semantic structure plus measured theme/font-only deltas on that unit; record any interim golden/expectation with owning migration unit, never claim its legacy Pencil comparison as Clubhouse certification. Migrate affected oracle inputs atomically with each page; don't disable tests or loosen budgets to keep a commit green.
- **Rollback/mitigation:** Before publishing, isolate failure at last accepted unit SHA; revert the last affected unit or correct within it, together with its manifests and regressions, and retest the changed state. For foundation regressions affecting descendants, fix or roll back the foundation with dependent units in reverse order; do not restore old globals underneath Clubhouse pages alone. For navigation/profile moves retain old deep links and usable action paths until approved replacements are present. Keep auth/mutation/policy contracts unchanged so UI rollback does not require data repair.
