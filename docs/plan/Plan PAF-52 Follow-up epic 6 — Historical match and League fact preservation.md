## Chosen Approach

- Proposed solution:
  1. Add one private SQL predicate `league_actor_has_participation(p_league_id uuid)` using caller `auth.uid()`: earned `league_player_counters` row with `matches > 0`, OR caller UUID in immutable confirmed-version teams of an event bound to that League. No membership, profile, registration, ownership, result submission, app-wide rating or statistics-summary lookup establishes participation. Confirmed Incomplete/ineligible groups still satisfy participation; pending/disputed-only proposals do not.
  2. Add additive migration replacing only four named reader bodies. Gate becomes current member OR private participation predicate; original authentication/provisional/not-found/version validation, ordering, snapshot/paging and aggregation logic stay intact. Predicate is `STABLE SECURITY DEFINER SET search_path = ''`, fully qualified, EXECUTE revoked from PUBLIC, anon, authenticated, service_role. Readers retain authenticated-only execution. No RLS/table grants widened, no lifecycle processing/rebuild triggered by reads.
  3. Add explicit server-derived `access_mode: 'member' | 'former_participant'` to detail result, not to every League DTO. Member branch wins when membership remains active. Detail community context becomes `{id,name,timezone}` for both modes: stop returning `creation_enabled` and `can_create` from `get_league`, since detail does not need community creation settings. Keep `LeagueCommunityDto`/list/create contracts unchanged. Return minimal context directly from community row plus League timezone; do not call settings-reading `league_community_dto` in detail.
  4. Reuse detail, live/final standings and version-history UI. Former mode gets translated read-only notice, back link to `/matches/past`, no community-statistics/previous-Leagues links, no audit/admin actions. `can_manage` remains computed by existing SQL authority, not client mode. Match-history League name links to existing detail using item community/League IDs.
  5. Add focused access integration tests and real-browser navigation regression in PAF-173. Then add one dedicated parameterized preservation certification suite in PAF-47, running fresh fixtures for leave and Admin removal and checking exact before/after rows plus production RPC reads.
- Justification for simplicity:
  - Considered globally widening membership/RLS: smallest textual edit but leaks whole private community, invalidates commands and list totals; rejected.
  - Considered new former-player endpoint, independent screen or access ledger: duplicates readers/presentation or introduces mutable authorization state; rejected.
  - Chosen private predicate + four reader replacements shares policy at one seam and preserves established errors/grants. Direct confirmation/version teams avoid an unnecessary dependency on rebuildable statistics projections. Existing indexes on League/event/confirmation and counter primary key should suffice; inspect scoped query plan before adding indexes, no speculative schema expansion.
  - Explicit detail mode avoids treating every non-manager as former (ordinary members are also non-managers) or trusting a forged query parameter. Minimal community context removes settings leakage without creating a second detail DTO branch.
