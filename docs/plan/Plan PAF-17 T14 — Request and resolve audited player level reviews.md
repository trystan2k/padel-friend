## Chosen Approach

- Proposed solution: Small `src/features/level-reviews/` slice using existing flat feature conventions, server-function/RPC boundaries, strict DTOs, immutable request content/terminal decision and separate insert-only `player_rating_admin_adjustments`. Existing match ledger remains match-only. Adjustment exposes literal event type `ADMIN_REVIEW_ADJUSTMENT` through unified rating timeline readers and audit views; links non-null review ID for this workflow. Minimal Platform Admin allowlist lives in DB; shared server access helper only if reused. Resolution runs one database transaction; notifications are added transactionally in PAF-151.
- Justification for simplicity:
  1. **Chosen:** dedicated typed adjustment evidence + merged reader/replay checkpoints. Keeps match-source validation, group counts, result explanations and League/statistics consumers intact. Bounded changes at existing projection seams are unavoidable.
  2. **Rejected:** generalize `player_rating_events`/all calculations into polymorphic nullable match/admin rows. Possible, but requires relaxing numerous source FKs/guards and touching every match-only reader/statistics join. Higher regression risk without current-scope benefit.
  3. **Rejected:** update current rating in TypeScript, append loose audit log, notify later. Non-atomic, races result confirmation, replay erases changes, and browser/runtime privilege exposure unacceptable. No queue, background worker, event bus or generic RBAC framework needed.

### Supporting contracts to freeze before coding

- Request shape: UUID, owner UUID, DB-captured submission current level and rating revision, requested min/max (`min=max` = exact), reason, nullable evidence, status, DB timestamps, decision actor/note, final approved target, adjustment ID. Separate creation/decision DTOs prevent client-controlled owner/current state/actor/time/status. Current snapshot stays immutable even when rating changes while pending; approval reads fresh current state. Owner history returns safe display fields; raw internal states restricted to Platform Admin audit RPC.
- Input bounds proposal: level range `[0,7]`, hundredth precision matching live display/internal precision; min≤max, finite numbers only. Do not reuse onboarding 0.1-step check accidentally. Reason/decision note 1–2000 Unicode code points after edge trimming; evidence ≤4000. Validate raw precision BEFORE numeric column coercion (avoid silent 7.001→7.00 rounding). SQL and TypeScript share boundary tests. Admin corrected exact target lies within requested range; if outside, return explicit error rather than silently approve a different request.
- Pagination: bounded keyset pages (default 20/max 50), deterministic `(created_at,id)` cursors; admin status filter allowlist, history cursor validated. Preview includes current rating revision; resolution submits expected revision. If another confirmation/adjustment changed state, return `stale_rating`, refresh preview, require confirmation again; never trust client before-state.
- Mutation identifiers: stable client command UUID for submit/resolution. Retry same command + same content returns original result; changed payload conflicts. Unique active request per owner enforced by partial unique index (five-state version includes under_review). Race two different submissions: exactly one succeeds, other receives stable duplicate error.
- Resolution: approve/reject requires nonempty note. Same approved request + exact prior decision fingerprint returns existing event/outcome after fresh authorization, regardless of now-stale preview revision. Opposite/modified retry fails conflict. Terminal cancellation/rejection cannot be approved; no terminal edits/delete/reopen. Owner cancellation available via explicit RPC, never writable resolution fields.
- Rate limit (§55 SEC-011): DB-side per-owner submission throttle, including canceled/rejected requests, serialized with submit lock. Proposal three newly created requests per rolling 24h; same idempotent retry not another attempt. Central SQL policy helper follows `player-add` policy-function pattern. Translate rate-limit error. No CAPTCHA/general rate-limit service.
- Security: no table write privileges for authenticated/service-role runtime on adjustment/admin-role evidence; only tightly scoped command RPCs. `SECURITY DEFINER SET search_path = ''`, fully qualified references, explicit execution grants/revokes, `auth.uid()` + anonymous/provisional denial inside each public RPC. New tables receive restrictive provisional-actor policies; prior one-time policy installation does not cover them. RLS owner/admin reads only; create own requests through guarded RPC. Never use user_metadata/route flags as authority.
