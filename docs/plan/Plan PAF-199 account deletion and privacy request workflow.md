## Chosen Approach

- Proposed solution: Authenticated intake + verified email/operator approval + an idempotent Supabase processor, retaining only deliberately classified historical facts on a separate non-login identity. Manual operator runbook for other privacy rights and non-Supabase systems.
- Justification for simplicity: Direct Auth deletion/cascades would block or erase required history. Retaining the old UUID with a blank profile or shared fake user lets known IDs link records, can collide in four-player match/uniqueness contracts, and leaves a login/profile surrogate. Replacing the whole application identity model or adding an external queue/operator dashboard is unnecessary: re-anchor only retained history, keep existing live identifiers and auth boundaries, and reuse leases, cron, and email.
- Components to be modified/created: versioned migrations, generated DB contracts, private privacy-request/processor feature, minimal profile UI and route wiring, existing public policy + locale keys, case/runbook and inventory docs, fixture/test suites. No new provider, secret in client, public destructive endpoint, new generic admin suite, or broad data rights portal.

### Request flow and roles

1. **Intake**: Own-profile entry with separate explicit confirmation showing what disappears, what historical facts may remain, loss of access, and withdrawal cutoff. A signed-in non-anonymous, non-provisional user can request/status/withdraw only for self using a validated command ID, method POST for mutations, trusted-origin/CSRF enforcement and no-store. DB derives subject from verified session identity, not submitted email/UUID. One open case per subject; retries return original receipt; cap fresh reopen attempts via a DB-scoped lock and short-lived rate window. No external email sent directly on request click. For unclaimed people, inaccessible or not-onboarded accounts, representatives and other rights, published email intake is independent of signing up/claiming. Acknowledge with neutral reference (no account existence disclosure), record receipt time and requested scope, route non-erasure rights to operator response.
2. **Verify**: For an account, operator obtains the existing address from trusted Auth records, not the request payload. Send a short-lived, random, single-use challenge via the operator mailbox to the existing verified address; require the valid challenge plus explicit confirmation, and for in-app initiated cases bind proof to the same case/account. Design the minimal handoff in A: use owner-only bounded approval tooling, store only a digest/expiry and proof result, not raw code in DB/logs; cancel expired/consumed proof; restrict attempts and start new verification if email, identity or target state changes. No authorization from request sender text, mere possession of an old session, `email_confirmed_at` alone, invitation knowledge or editable JWT metadata. For provisional/unclaimed, challenge the address independently of Auth claim; verify current server-side invitation ownership link and intended person privately. If address is mistyped, recycled, ambiguous, mailbox lost, or submitted by an agent, do not execute or disclose existence; use proportionate alternative evidence/representation checked by operator, escalate unresolved cases, never solicit passwords or routine ID copies. Identify no-Auth pending additions by the verified email through the same private case boundary, not publicly searchable matching; scope all matches and resolve duplicates/aliases deliberately.
3. **Review / ready**: Operator acknowledges, triages data/exception and ownership blockers; returns date expectation or clarification. Proposed no fixed grace delay; withdraw until execution is atomically claimed. Dry run defaults to read-only: show coarse disposition/ownership/storage counts and blockers for one opaque case; no IDs/object URLs in ordinary output. Explicit approve/arm binds a short-lived one-use confirmation to case, target, action, environment/project ref and plan/revision; mismatch/drift requires new plan/approval before any new destructive phase. No browser operator route or bulk tool: use narrow trusted operator command authenticated via server-side secret access (MFA for secret/project access), explicit project allowlist, fail closed on missing configuration, and local/test default. Community admins and general platform reviewers get no erasure powers. Service role is powerful by design; restrict access and log safe action/outcome codes, not credentials.
4. **Execute**: Durable transitions: `received -> verified -> ready -> executing -> app_data_erased -> supabase_erased -> closed` with `withdrawn`, `blocked` or explicit exception outcome; blocked cases keep a last-completed phase and explicit retry/next action. Operator approval alone can arm; existing Worker cron handles only armed or resumable work, with token/fence and bounded backoff, no authentication from query strings. Owner handoffs take effect in the relational unit, not in preflight. Freeze/deny and revoke access before dismantling dependencies. No auto-unfreeze after destructive start.
5. **Respond / purge**: In-app receipt is not proof of erasure. After account is gone, operator sends the final disposition over the verified email thread; do not depend on login. Record response date/outcome; say what was removed, what remains and why, outstanding processor or backup restrictions, and avenues to challenge a refusal. Confirm only proven phases; incomplete external work is tracked, not silently called complete. Keep address and evidence only in protected correspondence/active case handling for a purpose and owner-approved expiry. Unlink subject and destroy verification, object manifest, retry pointers and any re-identifying keys as soon as not needed; retain minimum non-identifying outcome/timing counts or code-only case records with enforced expiry. Random case ID is still personal if correlated with retained mail; do not label it anonymous while correlation exists. No ordinary logs with subject UUID/email, provider identifiers, token, endpoint, paths, free text or raw upstream errors.

### Migration and erasure design

**History identity.** Add an internal principal/participant anchor containing only its UUID and a live vs withdrawn discriminator. Backfill live IDs equal to Auth UUID to preserve existing live commands/joins without populating replacement profiles. Verify creation/backfill across signup/onboard, Google, confirmed/unconfirmed invite, pre-profile and provisional flows; only live Auth holders can create/use live identities. Historical FK edges needed after deletion target the anchor, not Auth/profile. Account-owned/authorization edges stay on real Auth or profile. Atomically re-key the retained subject to a cryptographically random new UUID, replace every typed/embedded historic reference under the existing lock hierarchy, and remove the old anchor. Use explicit ordered updates and selected deferrable constraints or guarded cascades where they preserve existing uniqueness; do not persist an old->new mapping or derive a tombstone from old UUID, email or hash. A duplicate case/resume cannot produce another tombstone: row lock plus phase commit is part of the same DB transaction. Use no tombstone if there is no justified history. The tombstone never signs in, owns an active resource, receives messages, appears in invite/directory/self/stat searches, or enters active membership/invites/Push/leaderboards. Keep only essential internal replay inputs for other players; publish a localized generic placeholder without a link or stable cross-match tombstone ID. Where possible use scope-local display keys unrelated to the internal UUID; distinguish multiple departed positions in one match without conflating identities.

**Pseudonymization vs anonymization.** A replaced ID is still pseudonymous if a mapping or reasonably available linkage remains (old API/log exports, known roster/date/venue, unique rating trail, identity in another user's text, small league, previous standings). Test with an authorized admin/member/opponent who knows the retired UUID and contextual facts, plus guest/other community access. Remove local joins/maps, redundant context, free text and stable display correlators, limit derived data; sanitize account activity even when logs/backups are controlled separately. Anonymous means no reasonably likely re-identification in the actual context, not just irreversible UUID generation. Where retaining a record as-is fails that assessment, restrict exposure and aggregate/suppress affected fields/rows where safe; if neither allows the required history, document the exact trade-off and block the case/acceptance pending owner decision. Do not promise that participants forget what they observed.

### Risk register

| Risk | Prevent / detect / recover |
| --- | --- |
| Wrong user, operator misuse, CSRF or abuse | Self-bound POST and live-session proof, per-subject lock/rate, challenge possession plus explicit approval, case/project/revision-bound dry run and one-time arm; no shared staff role, no public lookup/bulk delete. Minimal action codes and private operator response. |
| Partial failure or duplicate job after destructive step | Fenced step receipts, row/version locks and atomic relational checkpoint, exact-target rechecks and bounded retries; keep frozen until successful/reconciled. Disable queue/arming to mitigate, never resurrect erased users. |
| Re-identification, mixed-subject payloads, restored snapshots | Random internal re-key, no mapping, contextual/data minimization and audience testing, suppress disputed contextual disclosures; restricted, time-bounded recovery evidence only when necessary, gated restore with synthetic proof. |
| History corruption / protected or orphaned owner | Effective graph audit and ordered migration, accepted eligible handoff or explicit archive rule, rating/result lock parity and replay tests; no blind rewrites. Abort on drift or unapproved fallback and surface exact case blockers. |
| Access via stale JWT, orphaned Storage bytes or queued capability | Freeze incl. direct RLS/Storage and worker fences, live-session/existence gate, object API verification before Auth hard delete, revoke/reconcile in-flight work; test leaked/stale state cannot reattach or re-create. |
| Retention/compliance overstatement | Dated provider evidence, proof-based public language, no six-month promise, distinguish exceptions and legal-review status, segregate manually controlled copies; escalate unverified claims, do not schedule unrelated enhancements. |
