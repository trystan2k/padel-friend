## Implementation Steps

1. **Preflight/schema contract.** Confirm branch/base and no pre-existing community tables/matches schema; verify `pnpm exec supabase --version`, `pnpm exec supabase migration new --help`, then create one CLI-timestamped migration. Assume only authenticated identities have community content; guest means `anon`, while an authenticated nonmember can discover public _community basics_ only. Community IDs are UUIDs; `auth.users(id)` references use `ON DELETE RESTRICT` for historical actor/member continuity, not cascading erasure. No user-facing copy or design artifact. Check line budget before writing: target ≤800 changed lines total (including plan and generated types), ≤20 files; never sacrifice a security probe to meet gate—split issue/ask if estimate fails.
2. **Define schema and integrity in migration (all names `public.*`, timestamps `timestamptz`, IDs `uuid default gen_random_uuid()`).** Enums `community_visibility AS ENUM ('public','private')`, `community_member_role AS ENUM ('admin','member')`, `community_membership_status AS ENUM ('active','pending','inactive')`. `communities`: `id` PK; `name text NOT NULL` trimmed/nonblank length 1–80; `description text NULL` max 500; `logo_path text NULL` max 256 (reference only, no upload policy); `city_label text NULL` max 120; `visibility community_visibility NOT NULL`; `settings jsonb NOT NULL DEFAULT '{}'::jsonb` object-only, serialized size ≤4096 bytes; `created_by uuid NOT NULL REFERENCES auth.users(id) ON DELETE RESTRICT`; `created_at`, `updated_at` NOT NULL DEFAULT now(). Index `(visibility,created_at DESC)` for authenticated public discovery. Direct community INSERT/DELETE denied; creator RPC in step 4; only admin updates named/settings/visibility fields.
3. **Define dependent rows and interval constraints.** `community_members`: `id` PK, `community_id uuid NOT NULL REFERENCES communities(id) ON DELETE RESTRICT`, `user_id uuid NOT NULL REFERENCES auth.users(id) ON DELETE RESTRICT`, `role community_member_role NOT NULL DEFAULT 'member'`, `status community_membership_status NOT NULL`, `valid_from timestamptz NOT NULL DEFAULT now()`, `valid_until timestamptz NULL`, `created_at timestamptz NOT NULL DEFAULT now()`; `CHECK(valid_until IS NULL AND status IN ('active','pending') OR valid_until > valid_from AND status='inactive')`; unique partial index `(community_id,user_id) WHERE valid_until IS NULL` forbids second open/pending join; `(user_id,community_id,valid_until)` for own history and `(community_id,status,role,valid_until)` for active role checks. `community_invitations`: `id` PK, `community_id` restrictive FK, `invitee_user_id uuid NOT NULL` restrictive auth FK, `issued_by uuid NOT NULL DEFAULT auth.uid()` restrictive auth FK, `token_hash text NOT NULL UNIQUE` (fixed 64 lowercase hex characters; never store raw token), `expires_at timestamptz NOT NULL`, `redeemed_at timestamptz NULL`, `revoked_at timestamptz NULL`, `created_at timestamptz NOT NULL DEFAULT now()`; CHECK expiry > creation, redeem/revoke mutually exclusive, redeem no later than expiry; partial unique `(community_id,invitee_user_id) WHERE redeemed_at IS NULL AND revoked_at IS NULL` (expired outstanding invite requires explicit revocation before reissue); CHECK redemption/revocation timestamps are no earlier than creation; index invitee/expiry. No client grant to set redeemed_at or issued_by; later trusted join flow must atomically verify expiry, hash, audience and redemption. `community_venues`: `id` PK, `community_id` restrictive FK, `name text NOT NULL` trimmed length 1–120, `address text NULL` max 300, `maps_url text NULL` max 2048 with `https://` prefix, `photo_path text NULL` max 256 (storage integration deferred), `created_by uuid NOT NULL DEFAULT auth.uid()` restrictive auth FK, `created_at`,`updated_at` NOT NULL DEFAULT now(); index `(community_id,name)`. `community_audit_log`: `id` PK, `community_id` restrictive FK, `actor_user_id uuid NULL` (auth.uid() captured by trigger; NULL permits explicitly trusted maintenance, never client-written), `entity text NOT NULL` limited to four mutable community table names, `entity_id uuid NOT NULL`, `action text NOT NULL` limited to INSERT/UPDATE, `details jsonb NOT NULL DEFAULT '{}'::jsonb` with safe whitelisted state transitions only, `occurred_at timestamptz NOT NULL DEFAULT now()`; index `(community_id,occurred_at DESC,id)`. Do not put invitation token hashes, emails, arbitrary settings or full row snapshots into audit. No cascade on any community-scoped FK; prefer explicit future retention policy to silent history deletion.
4. **Implement helpers and non-bypassable bootstrap.** `public.is_community_member(p_community_id uuid)` returns boolean from indexed `community_members` where `user_id=(select auth.uid())`, `status='active'`, `valid_from<=now()`, `valid_until IS NULL OR valid_until>now()`; `public.is_community_admin(uuid)` same plus `role='admin'`; `public.can_read_community(uuid)` returns true iff `(select auth.uid()) IS NOT NULL` and community is `public` OR active member. Use `LANGUAGE sql STABLE SECURITY DEFINER SET search_path=''` with fully qualified names, explicit null-identity rejection and zero extra user-ID arguments; owner bypasses recursive members RLS intentionally. REVOKE function EXECUTE from `PUBLIC,anon`; GRANT to `authenticated` only; test `anon` RPC refusal. Private-match policy later becomes `FOR SELECT TO authenticated USING (public.can_read_community(community_id))` **only after PAF-4 defines which public match statuses are visible**; private branch remains active-member-only. `public.create_community(p_name,p_visibility,...)` authenticated-only SECURITY DEFINER RPC validates fields/identity and inserts community + initial active admin membership within one transaction, using `auth.uid()` rather than caller-supplied actor; no arbitrary owner/admin assignment; fully qualified names/search_path, revoke `PUBLIC,anon`, grant execute `authenticated`. Apply same membership audit trigger to bootstrap inserts, with actor captured from JWT. Explicitly deny anon signed-out content; if Supabase anonymous _signed-in_ identities become enabled later, also reject JWT `is_anonymous` in helpers/bootstrap (validate local config before enabling feature).
5. **Install table privileges and command-by-command RLS.** `ALTER TABLE` enable RLS for all five; `REVOKE ALL ON ... FROM PUBLIC,anon,authenticated` first, then explicit grants. `communities`: GRANT SELECT to authenticated; SELECT policy `can_read_community(id)` (public discoverable only to signed-in users); GRANT UPDATE only `(name,description,logo_path,city_label,visibility,settings)` to authenticated, UPDATE policy `USING is_community_admin(id) WITH CHECK is_community_admin(id)`; no direct INSERT/DELETE policy/grant. `community_members`: GRANT SELECT to authenticated; SELECT policy `user_id=(select auth.uid()) OR is_community_admin(community_id)` (own inactive/pending history visible; admins see roster); GRANT INSERT only `(community_id,user_id,role,status)` (server-default `valid_from` prevents client backdating/overlap) and UPDATE only `(role,status,valid_until)`; INSERT `WITH CHECK is_community_admin(community_id)`; UPDATE `USING is_community_admin(community_id) WITH CHECK is_community_admin(community_id)`; no DELETE. `community_invitations`: GRANT SELECT only safe columns **excluding token_hash** to authenticated (integration queries name explicit safe columns, never `select('*')` on invitations); SELECT `invitee_user_id=(select auth.uid()) OR is_community_admin(community_id)` (invited sees only own invitation; no community/venue/membership access); GRANT INSERT only `(community_id,invitee_user_id,token_hash,expires_at)`, UPDATE only `(revoked_at)`; INSERT admin WITH CHECK; UPDATE admin USING/WITH CHECK; no DELETE, redeem write reserved for future privileged flow. `community_venues`: GRANT SELECT to authenticated; SELECT `is_community_member(community_id)` (public nonmember sees only community basics, not venues); GRANT INSERT only `(community_id,name,address,maps_url,photo_path)` and UPDATE only `(name,address,maps_url,photo_path)`; INSERT/UPDATE admin WITH CHECK/USING, no DELETE. `community_audit_log`: GRANT SELECT to authenticated, SELECT admin-only; no INSERT/UPDATE/DELETE grants or policies. No `FOR ALL` shortcut or `anon` table privileges. Protect immutable IDs/creator/stamps via column grants plus invariant triggers, including if later privileged code writes them; verify UPDATE has SELECT visibility. Settings are **column on communities**, not a sixth table; admin-only update follows community UPDATE grant/policy.
6. **Enforce history, last admin and audit at database boundary.** BEFORE UPDATE guard on members: community/user/valid_from/created_at immutable; inactive rows immutable; only pending→active/inactive, active→inactive, or same status; inactive requires end > start, open states require NULL end; closing an active admin must leave another currently active admin. Serialize admin-closing/demoting changes by locking the parent community row (`SELECT ... FOR UPDATE`) **before** counting effective active admins; exercise simultaneous demotion in tests rather than assuming lock correctness. No authenticated DELETE grant/policy; add BEFORE DELETE trigger rejecting member deletion (including privileged paths), so rows only close and a rejoin inserts a new interval. Avoid ON DELETE CASCADE; document deliberate auth-user delete restriction and later account erasure design. BEFORE UPDATE guard on invitation disallows clearing `revoked_at`, changing identity/hash, or reopening redeemed/revoked invite; after expiry it remains unusable when future acceptance checks `expires_at>now()`. Generic small AFTER INSERT/UPDATE trigger for communities, members, invitations, venues writes append-only audit rows with `TG_OP`, entity ID, community ID, `auth.uid()` and whitelisted role/status/visibility/expiry-revocation changes; SECURITY DEFINER, empty search_path, revoke PUBLIC/anon/authenticated EXECUTE on trigger functions, no direct client audit writes. Trigger writes run in same transaction; failed unauthorized actions generate no audit. Admin can later read audit via PAF-31; member/nonmember cannot. Keep actor identity server-derived, never trust client-supplied actor/audit payload. If privileged maintenance needs a bypass, handle in separately reviewed future migration—not user-controlled flag.
7. **Generate types; build real role matrix.** Run `pnpm db:start && pnpm db:reset` against disposable local project; `pnpm db:types` after success; inspect generated enums, functions and all five tables. In `test/community.integration.test.ts` reuse `usableLocalEnv/localSupabaseEnv` logic and explicit `CI backend guard` describe from player suite: only `127.0.0.1`/`localhost`, environment wins over `.env`, missing vars skip with visible reason locally, `CI`+missing/nonloopback **fails**, `describe.skipIf` guarded resolver, no service-role or secret. Sign up fresh users via publishable key and create separate JWT-bearing clients (email confirmations disabled locally); use creator RPC and admin-authorized inserts to seed two communities and invitation/pending/inactive/active intervals, venue/settings/audit; no SQL bypass fixture. Create distinct actors: `public` = authenticated nonmember looking at public community, `private` = authenticated unsolicited nonmember probing private community, `invited` = private invitee with no membership, `pending` = pending member, `inactive` = ended former member, `member` = active member, `Admin` = active admin; add anonymous signed-out client. Use parameterized expectation table for public/private community, own membership/history, foreign roster, own invitation, venue and audit; filter by known private ID and also unfiltered list to catch leaks. An invited actor reads _only their own invitation_; pending/inactive read own membership but get no private community/venue or admin access. Positive admin inserts/updates membership/invitation/venue/settings; each nonadmin attempts direct INSERT and UPDATE on those resources (expect 42501 or zero rows as appropriate), forged owner/status/id/timestamp/token/select, forbidden DELETE and direct audit INSERT; verify rows unchanged as admin. Test member/admin helpers, first creator admin atomicity, duplicate open member rejection, expiry/revoke/redeem constraints, inactive row survival/rejoin new interval, final-admin demotion rejection, simultaneous two-admin demotions (exactly one survives), audit append/actor and denied reads.
