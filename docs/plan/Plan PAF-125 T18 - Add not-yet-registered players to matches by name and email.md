### Critical feasibility checkpoint — before dependent implementation

Admin invite HTTP and a subsequent SQL RPC cannot be one database transaction. A naive inviteUserByEmail → RPC sequence violates unknown-email atomicity. Proposed bridge: a one-use, server-only add operation prepared in SQL; Auth's auth.users INSERT trigger consumes its opaque capability and performs profile/rating/membership/registration writes inside Auth's own transaction. Failed registration must roll back new auth.users too. Preparing an operation/rate reservation beforehand is not creation of a partial player.

Before relying on this design, prove with installed local Supabase version:
1. Admin Invite insertion executes a transactional AFTER INSERT trigger with supported role privileges and server-supplied opaque operation capability. Public signup with forged metadata cannot consume it. Auth inserts/identities/confirmation fields remain GoTrue-owned, not handwritten SQL.
2. Trigger failure leaves no Auth user, public identity state or invitation email; invite email send failure/retry does not create a second UUID or roster row. Determine actual commit/mail ordering with fault injection rather than assuming it.
3. Re-inviting an existing unclaimed identity can send a verified invite/claim email without a second Auth user or overwriting profile. Verify supported resend/link mechanism; do not assume inviteUserByEmail accepts existing users.
4. Auth templates can render trusted operation-specific locale/inviter/event for repeated cross-community invitations without mutable global user-metadata races. If native templates cannot carry immutable per-send context, use a verified Send Email Hook with operation lookup and custom SMTP dispatch; that hook and authentication/retry tests belong in PAF-128, not future work.
5. Verified Google same-email linking retains UUID and rejects unverified provider email. Local provider fixture must drive real GoTrue OAuth callback/linking, not merely mock application getClaims.

These are technical verification gates, not evidence that requirements are impossible. If any fails and no supported bridge meets locked requirements, stop affected unit, report precise API/transaction trace and remaining ACs to parent. Unblocking condition: proven supported Auth integration or explicit product-owner revision. All six units remain current scope.

## Chosen Approach

- Proposed solution: Extend existing Supabase identity/registration architecture. Minimal protected operation ledger supplies idempotency, throttling and Auth transaction bridge; existing SQL writers own roster rules. Add localized Auth mail and restricted verified-claim onboarding. Reuse Base UI, StyleX tokens and current participant components.
- Justification for simplicity:
  1. Separate shadow-player identity/re-keying: rejected; violates permanent UUID and multiplies foreign-key/claim logic.
  2. Admin invite then profile/register RPC with compensating deletion: superficially simpler, rejected; cannot meet atomicity, safe retry and racing signup guarantees.
  3. Auth-owned identity INSERT plus narrow transactional provisioning trigger: chosen, subject to checkpoint. More bounded than replacing Auth, manually inserting auth.users or adding a general workflow/event-bus platform. One SQL command model, one existing registration path, one identity throughout.
- Components to be modified/created:

### Proposed supporting contracts

Names below are implementation contracts, not declarations that these functions exist today. Keep RPC payloads typed, server-only results private, search_path empty, fully qualify objects, explicitly revoke default PUBLIC execute.

- player_profiles: is_provisional boolean not null default false; provisional_initial_level numeric(3,1) check 0–7; source marker creator_estimated; invited_by UUID and source_match_event_id UUID provenance (protected from client mutation). Existing players backfill false, no rating rewrites. Preserve creator-estimated provenance after claim. Use EITHER preferred_side until claimant supplies real preference. Match profile/rating existence invariant from creation.
- Auth app_metadata: provisional mirror set only by trusted Auth path; profile DB state authoritative for SQL access. Never trust raw_user_meta_data or stale JWT marker for authorization. Do not clear provisionally restricted DB state merely on email confirmation.
- community_members: mark provisional provenance on active membership interval or derive provisional state from profile plus protected inviter/source metadata. Preserve role=member, activation interval, audit attribution and one-open-membership uniqueness. Claim turns existing memberships normal without leaving/rejoining/re-keying. Never silently reactivate a previously expelled membership; inspect existing lifecycle denial and surface conflict if locked cross-community rule cannot coexist with governance.
- prepare_match_player_add(p_match_event_id uuid, p_display_name text, p_email text, p_estimated_level numeric, p_locale text, p_request_id uuid) returns jsonb: authenticated RPC derives actor from auth.uid; validates actor/window/input and records request fingerprint. Executes known branches or reserves unknown operation. Public return contains only status/request identifier; any bridge capability stays in service-only fetch result, never browser response. Service-only fetch must bind actor/event/request to verified caller, not accept arbitrary user IDs from clients.
- complete_match_player_add_locked(p_operation_id uuid, p_user_id uuid) returns void: internal-only, canonical lock + fresh authz/window check; performs provisional rating/profile/member initialization as necessary and invokes existing invitation/registration writer semantics. Trigger invokes for unknown identity; known provisional invokes within prepare transaction. No authenticated/service-free execute grant on internal helper.
- get_match_player_add_operation(p_actor_id uuid, p_request_id uuid, p_event_id uuid) returns jsonb: service_role-only, returns dispatch/capability state for prepared operation. Service caller supplies actor only from validated claims; SQL rechecks event ownership/admin at execution.
- claim_provisional_player(p_display_name text, p_preferred_side text, p_initial_level numeric, p_dominant_hand text default null, p_bio text default null) returns void: authenticated restricted claimant only. Verify auth.users.email_confirmed_at and matching authenticated subject; do not accept a target UUID/email or trust client verified=true. Lock profile/rating; preserve history and rated initial state; audit and clear marker transactionally. Trusted server synchronizes Auth mirror idempotently after DB transition; DB remains security authority if mirror retry fails.
- Add-player browser result: identical { status: 'ok' } for successful registered/provisional/new branches and email-throttle suppression. No target UUID, existence flag, account name, email-delivery branch, raw Auth error or retry timing branch. Generic failures cannot depend on hidden identity type. Validation/authorization/window errors may use established codes; per-actor overload response must be identity-independent. Never return stored profile values to organizer through command.
- Private operation ledger: unique actor/event/request UUID, normalized-input fingerprint, state, target UUID, locale/inviter/event snapshot, capability hash/expiry, email eligibility and dispatch state. Reject same key/different input generically; same key retries do not repeat effects. Normalize email by trim/lowercase consistently with Auth's uniqueness; do not strip dots/plus tags. Avoid logging raw emails; private ledger only retains data required for Auth delivery.
- Rate-limit storage: Postgres private table keyed by actor or keyed normalized-email digest + window, with atomic upsert/locking. Proposed defaults: actor 20/hour; recipient 1 invite/15 minutes globally. These operational defaults are not locked product decisions; central constants + deterministic clock tests, document values. Count across events/communities and retries consistently, suppress duplicate recipient mail, audit throttle hits. Keep denial audit in committed transaction: returning suppression/result, not raising an exception that rolls back evidence. Service-only HMAC email key avoids exposing email hashes to public projections.
- Email dispatch: one eligibility record per logical add, globally throttled recipient; no second email from app plus GoTrue. Persist dispatch attempt/result without tokens. SMTP acceptance is not distributed exactly-once delivery: reconcile ambiguous outcomes without blind resend. Required proof is one emitted message per successful logical add, none on duplicates/throttle/failure paths; do not claim global exactly-once SMTP guarantees.
