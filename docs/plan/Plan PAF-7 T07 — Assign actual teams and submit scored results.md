## Chosen Approach

- Proposed solution: Extend the match domain with a **narrow result-proposal subsystem**: `match_event_result_proposals` (one active pointer row per event+group, carrying status `pending`, `active_version`, `review_deadline_at`) plus append-only `match_event_result_proposal_versions` (immutable full fact set: explicit 2+2 team assignment by user id, sequential set rows with completed flags, computed classification, played_at stored three ways — UTC instant, entered local timestamp, entered UTC offset — and optional court label). A pure scoring engine (SQL functions mirrored by TS validators) owns set legality (6–0…6–4, 7–5, 7–6 either orientation; normal third set only) and classification (win / rated Draw when completed sets are 1–1 with no completed third / Incomplete otherwise). One `submit_match_event_result` RPC reuses the canonical lock chain, invokes `protect_match_event_results` transactionally on first submission, validates the submitted four players exactly equal the frozen group's playing quartet (2 per team, no duplicates, Reserve Not Playing impossible), rejects a second stale submission with a typed active-proposal conflict carrying version + 48-hour deadline, and records request_id replay in the existing management-commands ledger. A three-step record-result UI (PLAYERS → SCORE → REVIEW per Pencil) renders suggested team pairing for confirmation/correction, per-set COMPLETE/IN PROGRESS rows, a predicted-outcome preview with rating-effect copy, and clearly identified invalid set/team errors; the pending state (`PENDING · NOT CONFIRMED`, auto-confirm countdown) renders from the proposal read.
- Justification for simplicity:
  1. **Selected: additive SQL + versions table on the existing domain.** Every hard problem (locking, authorization, idempotency, roster freezing, audit evidence) already has a proven contract from PAF-5/PAF-6; this approach reuses all of them and adds one purpose-built fact store. Frontend reuses the established model/validators/functions/error-copy module pattern and the management `correction` seam exactly as PAF-6 designed it.
  2. **Rejected: result columns on `match_event_registrations` or a derived teams table.** No versioning or stale-submission story, pollutes every registration projection/RLS surface, and couples played results to mutable-feeling roster rows.
  3. **Rejected: generic workflow/event-sourcing framework, new notification fanout, or a ratings-preview service.** The append-only versions table is the complete evidence chain; rating effects stay derived display copy until a later epic owns them; review notifications belong to PAF-8's review flow, not this one.
- Components to be modified/created: timestamped migrations below; `src/lib/supabase/database.types.ts`; `match-result-model.ts`, `match-result.validators.ts`, `match-result.functions.ts`, `match-result-error-copy.ts`, `match-result.styles.ts`, `RecordMatchResultPage.tsx`, pending-proposal summary integration in `MatchDetailPage.tsx`/management DTO consumer; `src/routes/_protected.matches.$eventId.record.tsx`; en/pt-BR/es catalogs; `test/helpers` + `e2e/matches-management-fixtures.ts` result fixtures; unit/integration tests and final E2E/visual suites. No global-reset styling changes, no route business logic.

### Missing Inputs, Assumptions Made, Targeted Clarifications

1. **Pencil composition gap (visual-gate prerequisite, not a functional blocker):** the design shows the Draw/unfinished-third outcome and competitive rating-effect composition, plus pending/auto-confirm states. No explicit compositions were found for a WIN outcome, an INCOMPLETE outcome, or a friendly "no rating effect" preview, and no per-set inline error compositions exist. T07.4 must re-enumerate frames via Pencil MCP, record exact IDs in the reference manifest, and — where a required state is absent — obtain design-owner approval for that state's composition before claiming the visual AC, following the T06 §7.1 precedent. Functional/backend work is unblocked.
2. **Predefined teams are a presentation concept, not stored state:** no pre-match team-pairing exists in the schema (PAF-5 derives quartets only). The UI suggests the order-based pairing (accepted_order 1&2 vs 3&4) as "suggested teams"; the server always requires the four players explicitly assigned 2+2. This satisfies both "predefined teams can be confirmed/corrected" and "post-match teams must be explicitly assigned" with one validation path.
3. **Stale-submission semantics (binding reading of AC7):** a submission for a group that already has an active proposal is rejected with a typed conflict carrying the active version and review deadline; it never overwrites and never bumps the version. Versions >1 exist structurally for the later correction/resubmission epics (append-only versions table); PAF-7 only ever creates version 1.
4. **No notifications in PAF-7:** the test plan and ACs contain no notification criterion; discovering a pending proposal happens through the match detail pending summary. Review-flow notifications (approve/reject/auto-confirm) belong to PAF-8. Recorded as a boundary, not deferred work.
5. **played_at validation rules:** must be a real local time in `event.timezone` (DST-ambiguous times resolved only with an explicit offset; nonexistent times rejected); must not be in the future by DB clock at submission; otherwise independent of `starts_at`, submission time, and any confirmation time by design (three separately stored clocks; nothing derives another).
6. **Court metadata:** one optional trimmed text label per group (e.g. "Court 3", 1..100 chars, no control characters). Not a venue foreign key — the PRD's "optional group court metadata" is free-text provenance.
7. **Command-ledger reuse:** result submission replays via `match_event_management_commands` with action `'submit_result'` (additive CHECK extension). If the orchestrator prefers not to touch the T06 constraint, the fallback is a `request_id` unique column on proposals with natural replay — decide before T07.3; do not build both.

No additional user decision is required. Disagree with assumptions 2–7 before coding the affected unit; do not silently omit affected criteria. Unrelated pre-existing defects are reported separately, never scheduled here.

### T07.2 — Server-side score validation engine and Draw/Incomplete classification

One paragraph: Implement the pure scoring engine twice, table-driven-parity tested: SQL functions (internal, EXECUTE revoked) `validate_match_result_sets(p_sets jsonb) RETURNS jsonb` (normalizes set rows, raises MATCH_RESULT_<TOKEN> with structured DETAIL carrying set index and offending side) and `classify_match_result_sets(p_sets jsonb) RETURNS text`; and the TS mirror in `match-result-model.ts`/`match-result.validators.ts`. Rules: 1–3 sets, sequential (set n+1 only if set n completed); a completed set is exactly 6–0…6–4, 7–5, or 7–6 in either orientation (6–5 invalid — a 5-game loser must lose 6 or lose the tiebreak path to 7–5/7–6); third set uses normal scoring only; classification: ≥2 completed sets → majority winner (`team_a`/`team_b`), exactly 1–1 completed with no completed third set → `draw` (an unfinished third-set row may be stored but cannot decide anything), fewer than 2 completed sets → `incomplete` (covers "one set only").

Acceptance criteria (own): every test-plan scoring fixture passes on both engines with identical outcomes; invalid 6–5 (and 7–4, 7–7, 8-x, out-of-order sets, non-sequential sets) rejected with set index + side detail; draw requires 1–1 with no completed third; 2–0 with a stored incomplete third set classifies as a win; one completed set classifies Incomplete; friendly/incomplete have no rating-effect semantics anywhere in the engine (classification only).
