## Chosen Approach

- Proposed solution: Checked-in second CLI project at **`test/stack/supabase/`**, project ID **`padel-friend-test`**, selected through an absolute `--workdir <repo>/test/stack` on every test CLI call. Keep root `supabase/` and dev project identity unchanged. Share canonical migrations, seed and email templates through checked-in relative symlinks. Resolve live test status once per launcher into validated in-memory environment; never overwrite developer `.env*`/`.dev.vars`.
- Justification for simplicity:
  1. **Chosen:** second normal CLI project, fixed port map, small built-in-Node helpers following existing `.mjs`/`.d.mts` conventions. Whole Auth/PostgREST/Storage/SQL surface is isolated; CLI retains lifecycle responsibility.
  2. **Rejected:** clone only a PostgreSQL database. Auth/PostgREST still address primary DB; cannot meet AC2/AC3.
  3. **Rejected:** custom Docker Compose, generated full config trees or CI/local dual targeting modes. More platform configuration and drift; unnecessary when CLI supports project ID + workdir. Static symlinks avoid maintaining copies or copying migrations on each reset.
  - Use package scripts for command sequencing and existing Node subprocess/test-injection patterns where validation/env propagation is necessary. No new framework, TOML dependency or generic stack manager.
- Components to be modified/created:
  - Unit 1: `test/stack/supabase/config.toml`, relative symlinks for migrations/seed/templates, `scripts/test-stack.mjs` (+ `.d.mts` if imported by TS), package lifecycle scripts, ignore rules and script/config regression tests.
  - Unit 2: shared status/env module and optional `scripts/with-test-stack.mjs` command wrapper; existing integration DB/build/runner/type/gate/fast-lane scripts and declarations; integration config, SQL/Auth/scheduler/OAuth helpers; E2E config/fixtures/spec credential and CLI call sites; release rehearsal/performance tooling and guard tests; isolation-proof helper/fixture.
  - Unit 3: `AGENTS.md`, `INITIAL_SETUP.md`, relevant example comments; CI workflow, composite startup action and CI contract tests as necessary. Root development URLs/examples stay 553xx. Scope lists are open-ended: follow remaining backend consumers found by step 1, not arbitrary file-count limits.
