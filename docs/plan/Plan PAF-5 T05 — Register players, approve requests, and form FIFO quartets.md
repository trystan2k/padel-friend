## Chosen Approach

- Proposed solution: Extend existing `match_event_registrations` into canonical event/user lifecycle ledger. Pending-request records live in this same table, distinguished from accepted participation; no second table that can race event/user uniqueness. Keep `accepted_at` for compatibility; add explicit request/approval anchors and immutable server-allocated accepted order. Mutate through small authenticated PostgreSQL RPCs, serialized per event; reconcile accepted roster and write notification effects in the same transaction. Separate registration DTO/read RPC from flat T04 event DTO. Add feature-owned UI; refresh authoritative data after actions.
- Justification for simplicity:
  - **Selected:** unified ledger + event lock + SQL reconciliation. Existing unique constraint covers pending and accepted, existing creator/publication flow remains authoritative, PostgreSQL supplies atomicity without distributed coordination.
  - **Rejected:** independent requests and registrations tables with only separate unique constraints. They permit simultaneous pending + accepted identity unless another identity table/trigger protocol is added; unnecessary complexity here.
  - **Rejected:** JavaScript count-then-insert or Worker queue/cache orchestration. Multiple RPCs cannot atomically protect last capacity slot or promote four players; distributed queues add infrastructure and eventual consistency.
  - Keep one narrow reconcile helper, one narrow cutoff processor and explicit action RPCs. No generic workflow engine, outbox for already-transactional in-app storage, realtime subscriptions or parallel shadow registration model.
- Components to be modified/created:
  - New timestamped migrations per domain/server/FIFO/cutoff unit; regenerate `src/lib/supabase/database.types.ts` whenever SQL surface changes. Never edit shipped migrations.
  - New `src/features/matches/match-registration-model.ts`, `match-registration.validators.ts`, `match-registration.functions.ts`; `MatchRegistrationPanel.tsx`, `MatchRequestQueue.tsx`, `match-registration.styles.ts` as needed. Existing detail/card/model and thin route integrations only.
  - Narrow notification target/context/heading updates, all three translation catalogs, colocated unit/integration suites under `test/`; final functional/visual suites under `e2e/`.

**Authoritative model / invariants**

- Keep unique `(match_event_id,user_id)` as identity across all states. Proposed lifecycle enum: `pending,accepted,rejected,expired,withdrawn` (withdrawn implementation gated by Q1); separate participation enum `playing,reserve,reserve_not_playing`, nullable for unaccepted/withdrawn records. Guest marking is registration source captured at acceptance; guest approval never inserts/updates `community_members`.
- Columns: `requested_at`, nullable `approved_at`, nullable existing `accepted_at`, nullable `accepted_order bigint`, lifecycle, participation status, registration source/request type, resolution actor/time. Explicit CHECKs forbid pending rows with accepted anchors/status/order; accepted approval rows require `approved_at = accepted_at`; direct/creator rows do not invent an approval. Preserve acceptance anchors on terminal history where appropriate, but exclude inactive records from active count.
- Add narrow `match_event_registration_state` table (event PK, next accepted ordinal, transition revision, cutoff_processed_at); initialize from existing accepted rows and create through publication trigger. Avoid modifying immutable match-event facts to store processing metadata. Unique `(event,accepted_order)` for nonnull orders. Backfill deterministic historical order `accepted_at,id`; creator stays first.
- Allocate order/time only after winning event lock. Direct acceptance: DB acceptance time. Approval: DB approval time copied to accepted_at. Pending requested_at never participates in queue/capacity. Retry returns original approval result/time/order. Ordinal breaks clock/timestamp ties and never gets renumbered; retain ordinals/gaps on withdrawal. Existing historical timestamp ties retain their deterministic migration order.
- Active N = lifecycle accepted rows only. Before cutoff: first `floor(N/4)*4` by accepted_order are Playing; remaining 0–3 Reserve. Maximum applies to all active accepted players, including creator and Reserve, not pending requests. Unlimited events remain open after 4, 8, etc.
- Canonical transaction lock order for any path that also needs community state: community → match event → registration state → affected registration rows ordered deterministically. Preserve T04 community-before-event publication order; scheduler uses same order. Event `SELECT … FOR UPDATE` is sufficient for joins on existing events. No mixed row-lock/advisory order inversions.
- Write authorization is self/creator semantics inside RPCs, with creator-only decisions; **do not grant browser raw DML** that can forge approvals/timestamps/statuses/capacity. RLS protects reads; SECURITY DEFINER has empty search_path, qualified relations, explicit UID/nonanonymous checks and revoked internal EXECUTE. Event-visible accepted roster is exposed through safe profile projection, not widening player-profile RLS globally. Pending requests/resolution metadata visible only to requester/creator; community Admin is not automatically approver.
- Strict cutoff comparison uses DB wall clock **after lock acquisition**: new joins/requests/approvals require `clock_timestamp() < registration_cutoff_at`. Equality is closed; a transaction begun earlier but blocked past cutoff loses. Exact already-completed approval replay remains a no-op success after cutoff; no late promotion/new timestamp.
