## Chosen Approach

- Proposed solution: Add typed `public.community_join_policy` enum `('instant', 'admin_approval')` and `communities.join_policy community_join_policy NOT NULL DEFAULT 'admin_approval'::public.community_join_policy`. Conservative backfill for existing rows; no coupled visibility/policy constraint: all four combinations are allowed, while private access remains controlled by existing RLS regardless of policy. PostgreSQL enum + NOT NULL enforce valid values; keep `settings jsonb` for other bounded settings, never join policy. Drop the exact old `create_community(text, public.community_visibility, text, text)` signature and recreate **one** function with required third `p_join_policy public.community_join_policy` before optional description/city arguments; insert `join_policy` alongside existing fields and preserve auth checks, `search_path = ''`, fully qualified names, atomic creator/admin inserts and UUID return. Revoke `EXECUTE` from `PUBLIC, anon, authenticated` on the new signature; grant only `authenticated`. No overload: avoids PostgREST ambiguous resolution and leaves only one typed RPC surface; migration must replay atomically and update all old callers. Existing `community_member_guard` still populates `activated_at`; `valid_from` uses DB `now()`, `valid_until` stays NULL. Grant authenticated `UPDATE(join_policy)` on `communities` in the new migration; current admin UPDATE policy, SELECT policy, timestamp/audit triggers and other grants remain intact. Do **not** change the applied PAF-26 migration.
- Justification for simplicity: (A) **Chosen**: extend the existing atomic RPC for create and use a single direct RLS-guarded UPDATE for settings; validator and returned-row check make boundary failures explicit with no new privilege. (B) Direct two-step inserts rejected: community INSERT is denied, and a gap/partial state would compromise bootstrap. (C) New SECURITY DEFINER settings RPC or preflight Admin check rejected: extra bypass surface, DB logic, and time-of-check/time-of-use race. Brainstormed edge cases: anonymous/missing claims, invalid enums/UUID/unknown keys, empty updates, optional nullable fields, JSON object/size, changing visibility without weakening private reads, multiple creations, missing/private community IDs and revoked/demoted admins. A zero-row UPDATE yields the **same** `NOT_COMMUNITY_ADMIN` for non-admin and unknown ID, preventing an existence oracle; report DB errors separately, never mistake them for successful writes.
- Components to be modified/created (exact intended list, **seven files**; migration timestamp is CLI-generated, not guessed):
  - **NEW** `supabase/migrations/<CLI-generated-timestamp>_community_join_policy.sql` — enum, defaulted NOT NULL column, explicit new UPDATE column grant; drop exact old function; recreate tightened one-signature RPC and execute revoke/grant. No edits to PAF-26 SQL.
  - **CHANGED/generated** `src/lib/supabase/database.types.ts` — `pnpm db:types` adds `communities` Row/Insert/Update join_policy, `community_join_policy` enum and required `p_join_policy` in `create_community.Args`; no manual edits.
  - **NEW** `src/features/community/community.validators.ts` — unknown-to-typed create/settings inputs; strict allowlists, SQL-aligned text/JSON limits and `INVALID_COMMUNITY_INPUT`.
  - **NEW** `src/features/community/community.functions.ts` — POST `createCommunity`, POST `updateCommunitySettings`; auth helper, typed RPC/direct UPDATE, stable errors and minimal returned DTOs.
  - **NEW** `test/community.functions.test.ts` — mocked Start builder and server client, real validators/auth helper, fail/success wiring and zero-row authorization tests.
  - **CHANGED** `test/community.integration.test.ts` — all old RPC calls updated (including anonymous-denial/invalid enum), join-policy and interval assertions, real-JWT function-handler integration scenarios reusing its existing loopback/CI guard and actors; keep existing role matrix intact.
  - **NEW** `docs/plan/Plan PAF-27 PAF-2.2 — Server functions: community create, settings, initial Admin assignment.md` — this plan. No CI/package/coverage-threshold changes.

4. **Validate inputs with SQL parity.** `validateCreateCommunity(value: unknown)`: exact allowlist `name,visibility,join_policy,description,city_label`; require name nonblank, 1–80 PostgreSQL code points, no ASCII edge whitespace per SQL `btrim(..., E' \t\n\r\f\v')`; exact enum values; optional description nullable max 500 and city_label nullable max 120; reject unknown keys, wrong/null required fields and overlimits with `INVALID_COMMUNITY_INPUT`. `validateUpdateCommunitySettings(value: unknown)`: require UUID `community_id`, at least one mutable field, allow only `name,visibility,join_policy,description,city_label,logo_path,settings`; reuse corresponding validation, logo_path nullable max 256, settings non-null plain JSON object (not array), JSON-serializable and ≤4096 UTF-8 bytes approximately, with DB JSONB CHECK as final authority.
