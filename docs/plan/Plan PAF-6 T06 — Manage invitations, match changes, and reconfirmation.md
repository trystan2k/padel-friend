2. Capture clock_timestamp **after locks** for writes; now()/one as_of remains valid for pure read snapshots. All leave/remove/edit/reconfirm/new entry/approval/decline/transfer before cutoff and start; cancel allowed after cutoff but before start. All management action RPCs reject start/cancel/result-protection before command replay. Existing completed operations remain durable evidence, but replay after start/cancel returns unavailable rather than reopening participation. Cancel exact same-command replay before starts_at may return cancelled no-op; at/after starts_at even that replay is rejected. No alternate cancellation after terminal state. Internal cron may persist due bookkeeping after start only if no protected result would be affected; see Step 6.
3. Reuse command request_id for network retries of the same intent; generate a new id for a fresh intent. Include attempt_id/generation so replay cannot withdraw/remove/reconfirm a later re-entry. Stale attempt fails before touching current identity. Identical command replay before the action deadline does not bump revision/version/audit or fanout. Natural invitation replay checks original response and submission_result. Double accept/decline serialize on same event; only first transition wins; pending expiry uses the same clock/lock.
4. Withdraw vs join: whichever wins lock sees current accepted capacity; reconcile once per roster mutation. No ordinal renumbering, reuse, or decrement. Queue positions are row_number over accepted_order,id among eligible active rows; gaps are correct. A removed #2 followed by a new #10 remains #10; history retains #2. Capacity failure consumes no ordinal/attempt/response/revision.
5. Remove vs cutoff: lock winner before deadline can remove; contender that acquires at/after cutoff rejects even if request started earlier. Cutoff processor expires pending invites/requests, excludes unreconfirmed, reconciles once, then writes marker/effects atomically. No reopening/reset of cutoff_processed_at. Edits only while old cutoff still future and unprocessed, with new cutoff strictly future and < new start. Moving cutoff changes derived invitation expiry; scheduler selects current value.
6. Cancel vs edit/reconfirm/transfer: event lock + expected_version for event mutations gives a single winner. Reconfirm checks cancelled and generation after acquiring lock; cannot restore a cancelled participant. No partial event edit, audit, command, or notification on conflict. Transfer/cancel increment version once; participation-only changes increment transition_revision, not event version. Edits increment version once when fields genuinely change. Reconcile owns transition_revision increments for roster changes; nonroster management commands advance it once through narrow internal revision helper, never plus a second reconcile bump.
7. Reconcile remains the **only UPDATE writer of participation_status**. Action RPCs may insert accepted rows with provisional reserve as existing code does, but do not directly assign playing/demotions. To clear departure/consent/cancelled rows, reconcile first sets NULL on ineligible rows, then computes eligible roster and effects. Callers stage lifecycle/consent first. Capture prior participation **and quartet membership** with internal snapshot_match_registration_roster_locked(p_event_id uuid) RETURNS jsonb before staging any lifecycle/consent changes; pass that snapshot to reconcile as new optional p_before_roster jsonb DEFAULT NULL (internal-only, validated shape). Null defaults preserve existing entry callers; all departures/major edits/cutoff exclusions/cancellations explicitly pass the pre-mutation snapshot. Use explicit prior member arrays to detect group membership changes, not just before/after headcount. Same headcount can change a quartet after removal. Emit new match_registration_group_changed for all surviving members whose quartet membership changed; existing promotion/reserve/quartet-complete effects remain for genuine transitions only, never for unchanged complete groups. Tests enforce exact recipient sets.
8. Result race contract: protect_match_event_results takes the same lock and validates status; cancellation checks results_protected_at after locking. Protection-first rejects cancellation; cancellation-first causes protection/result insertion to reject. Future result writer must make protection hook and result insert one transaction. This is testable now with privileged protection fixtures, not a claim that PAF-7 exists.
